## 사용자 스펙 의도

- 디자인 베이스 위에 프로덕트 디자이너의 전문 기준을 둔다.
- 사용자 맥락, 정보 구조, user flow, 상호작용 상태, 접근성, 반응형 품질을 다룬다.
- 같은 맥락에서 같은 용어·색상·패턴을 반복하고, 맥락에 따라 문구를 생략하거나 재제공한다.

# product-designer 스킬 스펙

## 목적과 경계

- 과업, 흐름, 조작, 상태, 피드백, 오류 예방·회복을 설계한다.
- 앱·SaaS·대시보드·폼·설정·온보딩·운영 콘솔에 적용한다. 웹 구현 여부는 역할 선택 기준이 아니다.
- 제품 범위·정책을 임의 확정하거나 코드·테스트 구현 절차와 출시 승인을 소유하지 않는다.
- 대표 표면: `skills/product-designer/SKILL.md`.

## 핵심 처리 계약

- 사용자 목표, 숙련도·빈도·환경·위험, 정책·권한·데이터·저장 계약과 기존 패턴을 확인한다.
- 진입 > 이해 > 선택 > 행동 > 피드백 > 완료·복귀·회복의 흐름과 상태 전환을 연결한다.
- 중요한 정보·빈번한 행동·위험 행동·상세 진입의 위계를 정한다. 비교가 핵심이면 밀도를 일률적으로 낮추지 않는다.
- 표·차트·로그·관계도는 단위·축·범례·행·노드·연결·방향·그룹을 읽을 수 있어야 한다.
- 정상·loading·empty·error·disabled·permission·success·partial success·cancel·interruption의 관련 상태와 다음 행동을 설계한다.
- 저장·전송·선택·취소·재시도·되돌리기의 규칙, 진행 상태, 입력 보존을 명확히 한다. 실제 미지원 기능을 약속하지 않는다.
- 문구는 라벨·CTA·안내·오류·상태·비용·결과·가역성을 실제 계약에 맞게 전달한다.
- 같은 의미·역할·상태는 용어·색·컴포넌트·조작 패턴을 반복한다. 낮은 그룹 위계 때문에 focus·오류 가시성·조작 목표를 약화하지 않는다.
- 스크롤·독립 상세·viewport·보조기술에서 맥락을 잃으면 필요한 라벨·단위를 복원한다.
- 실제 화면·동작과 가설을 구분한다. 확인하지 않은 흐름·접근성·효율을 검증 완료로 보고하지 않는다.

## 출력과 검토 질문

- 과업·흐름·필요 상태·상호작용·문구 결정, 관련 패턴과 검증 근거를 제공한다.
- 정책이 미정이면 디자인 가정과 확정이 필요한 결정을 구분한다.
- 사용자가 결과와 저장 상태를 알고, 실패 후 맥락과 입력을 유지하며 복구할 수 있는가?

## 독립성·확장

- bundle 내 직접 실행 가능. 프로젝트 맥락, design-base의 상호작용·문구, 공간·표면, 반복 reference를 명시적으로 읽는다.
- 색은 관련 결정이 있을 때 추가로 읽는다. planner나 다른 skill의 선행 실행은 필요 없다.
- 새 기준은 과업 수행과 상태 이해의 문제에 연결한다.
