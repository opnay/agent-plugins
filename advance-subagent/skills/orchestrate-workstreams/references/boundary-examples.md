# Boundary Examples

Skill selection decides whether to use orchestration. Once selected, use the same loop for one or several branches; do not add an internal direct route.

| Request or state | Selection or round behavior |
| --- | --- |
| Explicit orchestration, subagents, or fork-and-flush request | Enter the loop; design useful bounded work without a minimum branch count. |
| Independent modules or execution paths | Select when distinct meaningful tasks and verification make orchestration useful. |
| Different review lenses on the same code | Read-only partition with separate deliverables; integrate evidence and conflicts. |
| Same objective, competing methods | Alternative branches with common comparison criteria; preserve evidence from all methods. |
| Underspecified request in an active loop | Assign request interpretation, evidence discovery, or criterion formation; do not require a settled goal first. |
| One remaining task or one sequential cause | One branch or prerequisite scheduling inside an active loop. Ordinary sequential work alone does not automatically select this skill. |
| Mixed research and implementation | Attach each domain contract and authority; wait if implementation depends on research findings. |
| Deep research lead invocation | Always attach the research contract and use this loop, including question clarification and report checks. |
| Assigned research worker | Apply the bounded research contract without starting another loop. |
| Different implementation alternatives | Use isolated writable surfaces and runtimes; otherwise read-only comparison or sequential scheduling. |
| Complexity, file count, or generic implementation alone | Do not automatically select orchestration. |
| Simple lookup or one-source summary | Do not automatically select either orchestration or deep research. |
| User forbids agents or the tool lacks fresh execution | Respect the constraint and disclose the limitation; do not claim a fork or flush occurred. |
