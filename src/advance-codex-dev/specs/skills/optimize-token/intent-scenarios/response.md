# Response Intent Scenarios

이 문서는 `optimize-token`의 응답 압축 강도 선택을 검증하는 의도 시나리오입니다.
각 시나리오는 같은 입력에 대해 호출자가 `light`, `standard`, `extreme` 중 어떤 모드를 선택했는지에 따라 달라지는 출력 차이를 고정합니다.

## 판정 기준

- 호출 모드가 명시되면 그 모드를 따릅니다.
- 호출 모드가 명시되지 않았을 때만 요청과 위험도에 맞는 가장 약한 충분한 압축 강도를 추정합니다.
- `light`는 의미와 자연스러운 문장을 유지하면서 불필요한 표현을 줄입니다.
- `standard`는 핵심 판단, 근거, 다음 행동, material risk를 선별해 더 조밀하게 씁니다.
- `extreme`은 상태값, 라벨, 한 줄, 고정 필드처럼 매우 짧은 형태로 씁니다.
- 어떤 강도에서도 검증 실패, 미검증, 승인 경계, 파일 경로, 명령어, 날짜, 버전, 수치는 삭제하지 않습니다.
- 압축 결과가 원문보다 더 모호하면 실패입니다.

## 시나리오

### 일반 간결화

- 요청: `짧게 말해줘.`
- Before: `확인해 보니 설정 파일의 경로가 실제 파일 위치와 일치하지 않아서 문제가 발생했을 가능성이 높아 보입니다.`
- light: `설정 파일 경로가 실제 위치와 다릅니다.`
- standard: `설정 경로가 틀렸습니다.`
- extreme: `원인: 설정 경로 불일치.`
- 모드 차이: `light`는 자연문, `standard`는 더 직접적인 원인 문장, `extreme`은 라벨형 원인 표기로 고정합니다.

### 말투와 형식 보존

- 요청: `군더더기 없이 정리해줘.`
- Before: `전체적으로 보았을 때 이 변경은 요청하신 범위 안에 있으며, 특별히 추가로 설명드릴 만한 큰 문제는 없어 보입니다.`
- light: `이 변경은 요청 범위 안에 있습니다. 큰 추가 이슈는 없습니다.`
- standard: `요청 범위 안입니다. 큰 추가 이슈는 없습니다.`
- extreme: `범위: 적합. 이슈: 없음.`
- 모드 차이: `light`와 `standard`는 자연스러운 문장을 유지하고, `extreme`은 상태 라벨로 전환합니다.

### 긴 보고 축약

- 요청: `핵심만 요약해줘.`
- Before: `세 파일을 수정했고, 테스트는 두 개 실행했습니다. 첫 번째 테스트는 통과했지만 두 번째 테스트는 네트워크 제한으로 실행하지 못했습니다. 따라서 기능 자체는 확인됐지만 외부 연동 경로에는 아직 불확실성이 남아 있습니다.`
- light: `세 파일을 수정했고, 한 테스트는 통과했습니다. 외부 연동 테스트는 네트워크 제한으로 실행하지 못해 불확실성이 남아 있습니다.`
- standard: `세 파일을 수정했고 핵심 테스트는 통과했습니다. 외부 연동 테스트는 네트워크 제한으로 미실행이라 해당 경로는 불확실합니다.`
- extreme: `수정: 3파일. 검증: 핵심 통과, 외부 연동 미실행. 리스크: 외부 경로 불확실.`
- 모드 차이: 세 모드 모두 검증 결과와 residual risk를 보존하되, `standard`부터 배경을 강하게 줄이고 `extreme`은 필드형으로 고정합니다.

### 리뷰 결과 압축

- 요청: `리뷰 결과만 짧게.`
- Before: `가장 중요한 문제는 에러 처리 경로에서 null 값이 들어올 때 예외가 발생할 수 있다는 점입니다. 이 문제는 사용자 입력이 비어 있을 때 재현될 수 있으며, 현재 테스트에는 해당 케이스가 없습니다.`
- light: `가장 큰 문제는 null 입력에서 예외가 날 수 있다는 점입니다. 빈 입력 테스트가 없습니다.`
- standard: `주요 문제: null 입력에서 예외가 날 수 있습니다. 빈 사용자 입력 테스트가 없습니다.`
- extreme: `문제: null 예외 가능. 테스트: 빈 입력 없음.`
- 모드 차이: 세 모드 모두 버그 조건과 테스트 공백을 남기며, `extreme`만 라벨형으로 압축합니다.

### 상태값 요청

- 요청: `상태만.`
- Before: `검증은 아직 실행하지 않았고, 변경 범위가 넓어서 회귀 위험이 남아 있습니다.`
- light: `검증은 아직 실행하지 않았고, 넓은 변경 범위로 회귀 위험이 남아 있습니다.`
- standard: `미검증이며, 넓은 변경 범위로 회귀 위험이 남아 있습니다.`
- extreme: `상태: 미검증. 위험: 넓은 변경 범위.`
- 모드 차이: 세 모드 모두 미검증과 위험을 남기며, 선택 모드가 강해질수록 문장형에서 라벨형으로 이동합니다.

### 고정 필드 요청

- 요청: `파일/검증/리스크만 한 줄씩.`
- Before: `설정 파일과 테스트 파일을 수정했습니다. 검증은 단위 테스트를 실행해 통과했고, 남은 위험은 브라우저에서 수동으로 확인하지 못했다는 점입니다.`
- light: `설정 파일과 테스트 파일을 수정했습니다. 단위 테스트는 통과했고, 브라우저 수동 확인은 아직 하지 못했습니다.`
- standard: `파일은 설정과 테스트, 검증은 단위 테스트 통과, 리스크는 브라우저 수동 확인 미실행입니다.`
- extreme: `파일: 설정, 테스트. 검증: 단위 테스트 통과. 리스크: 브라우저 수동 확인 미실행.`
- 모드 차이: 세 모드 모두 `파일`, `검증`, `리스크` 축을 보존하며, `extreme`은 요청 필드를 라벨로 직접 맞춥니다.

### 승인 경계 보존

- 요청: `최대한 짧게.`
- Before: `커밋은 아직 실행하지 않았고, push와 PR 생성도 승인되지 않았습니다.`
- light: `커밋은 아직 실행하지 않았고, push와 PR도 승인되지 않았습니다.`
- standard: `커밋 미실행. push/PR 미승인.`
- extreme: `커밋: 미실행. push/PR: 미승인.`
- 모드 차이: 선택 모드가 강해져도 실행 여부와 승인 경계는 삭제하지 않습니다.
