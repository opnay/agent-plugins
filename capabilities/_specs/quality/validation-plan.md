# Quality 검증 계획

이 문서는 plugin·skill 설계와 향후 runtime의 검증 기준을 소유합니다. 설계 정합성, 실제 설치·로딩, 행동 계약 충족, skill의 추가 효과를 별도로 평가합니다. 계획과 미실행 사례를 성공 결과로 취급하지 않습니다.

## 1. 설계와 패키징 정합성

- plugin 목적과 단일 verify의 책임이 일치하며 단계별·분야별 중복 skill을 만들지 않습니다.
- skill은 열린 산출물 범위, 특성 기반 축·기준·방법 도출, 실제 실행과 근거, 판정·종료·권한 계약을 포함합니다.
- 분야 지식·도구·역할 skill·orcat·오케스트레이터·subagent는 숨은 필수 의존성이 아닙니다. 실제 필요한 근거·기능이 없을 때의 미완료 동작이 정의돼야 합니다.
- 기존 plugin과 skill은 변경하지 않습니다. 기존 pro-quality-manager의 교체·제거·migration은 별도 범위로 평가합니다.
- 구현 단계에서만 runtime frontmatter·리소스·두 manifest 공통 metadata·README·실제 호출·marketplace 등록을 대조하고, 기존 목록 순서를 보존합니다.
- 독립 설계 검토는 spec을 좁은 책임 영역으로 나눠 읽기 전용으로 수행합니다. 모델 행동 검증과 구분합니다.

## 2. 대표 사례 계획

아래 사례는 검증 설계입니다. 실행 전 실제 fixture·버전·기준·모델·권한·도구·예산을 확정해야 하며 현재 표만으로 비교 실험을 완료하거나 fixture를 고정한 것으로 보지 않습니다.

| ID | 유형 | 초기 산출물·조건 | 확인할 계약과 관찰 가능한 결과 |
| --- | --- | --- | --- |
| Q01 | 일반 | 동작 테스트는 통과하지만 테스트 편의를 위한 public export가 있는 코드. fixture의 저장소 규칙은 production 소비자 없는 공개 표면을 금지합니다. | 동작 외 구조·소유 기준을 선택하고 규칙·실제 소비자를 확인해 문제를 근거로 제시합니다. 테스트 통과만으로 전체 통과하지 않습니다. |
| Q02 | 일반 | 좁은 화면에서 주요 동작이 잘리는 화면과 확인 가능한 실제 렌더. 핵심 과업·대상 크기가 제공됩니다. | 실제 화면을 관찰하고 특성에 맞는 시각·조작·반응형 검증을 수행합니다. source 확인만으로 시각 검증 완료를 주장하지 않습니다. |
| Q03 | 일반 | 목표·대상 독자·제약은 있지만 수용 기준이 없는 비실행형 계획 문서. 본문에 요구와 실행안의 모순이 있습니다. | 목적에서 필요한 기준을 도출하고 추론한 기준을 표시합니다. 논리·요구 적합성을 실제 본문과 대조하고, 중요 정책 공백은 판정 유보로 남깁니다. |
| Q04 | 미사용 실패 가설 | 여러 출처가 같은 원본을 반복하고 일부 인용이 결론을 지지하지 않는 조사 결과. 확인 가능한 원본 fixture를 제공합니다. | 주장·출처·지지 범위·독립성을 대조합니다. 문서 완성도나 출처 수를 근거 충분성으로 대체하지 않습니다. |
| Q05 | 미사용 실패 가설 | 기능·구조·시각·수치가 섞인 결과물. 관련 기능 테스트는 통과하나 핵심 수치나 다른 상태의 명시 요구가 어긋납니다. | 하나의 분야·검사에 머무르지 않고 중요한 복합 특성에서 검증 축을 도출합니다. 결함을 다른 성공으로 상쇄하지 않습니다. |
| Q06 | 미사용 실패 가설 | 원본 읽기만 허용되고 중요한 검증에 필요한 도구·접근이 없는 산출물. 실행 도중 환경 실패가 발생할 수도 있습니다. | 허용된 근거로 가능한 부분을 확인하고 나머지는 not-run/inconclusive와 영향으로 반환합니다. 설치·외부 변경을 임의 수행하지 않고 환경 실패를 대상 결함으로 판정하지 않습니다. |
| Q07 | 미사용 실패 가설 | 검증 도중 버전이 바뀌는 산출물과 작성자의 기존 통과 보고서. 변경된 특성이 이전 보고서의 확인 범위 밖입니다. | 대상 식별·근거 유효성을 확인하고 변경 전 성공을 새 버전에 적용하지 않습니다. 중요 근거를 직접 재확인하거나 미검증으로 남깁니다. |
| Q08 | 일반 | 구체 산출물의 검증 계획만 요청합니다. 실행 가능한 fixture와 도구는 있으나 실제 검증 실행은 요청하지 않았습니다. | 축·기준·방법·관찰할 증거·실패 조건을 계획하고 실행 결과로 표현하지 않습니다. 추가 실행·수정·위임을 시작하지 않습니다. |
| Q09 | 일반·성공 대조 | 목적·검증 범위·단위·반올림 규칙이 명시되고 수량·단가·합계가 정확한 작은 수치 문서. 독립 재계산으로 fixture의 적합성을 사전 확인합니다. | 양쪽에서 같은 요구와 원본 근거로 충족을 판단하고 기존 성공을 보존합니다. 사용 조건이 무관한 필수 축·기준을 만들거나 결함을 꾸며 내지 않는지 확인합니다. |

Q09는 알려진 적합 산출물에 대한 성공 대조 사례입니다. fixture의 정확성과 실제 미사용 실행의 성공은 구분합니다. 미사용이 실패하면 원인·환경·기준을 확인하고 이를 성공 기준선으로 간주하지 않습니다. 실제 미사용 성공/사용 실패는 회귀로 기록하고, 두 조건이 성공한 경우 추가 효과는 미확인으로 남깁니다. 성공을 얻기 위해 요청·기준을 사후 완화하지 않습니다.

실패 가설 사례의 baseline 실패는 예측이며 관찰 결과가 아닙니다. 미사용 성공과 사용 실패를 그대로 기록하고, 결과에 맞춰 사례나 판정 기준을 바꾸지 않습니다.

## 3. 실행 전 고정할 조건

각 사례의 ID·유형·검증 계약·사용자 요청·초기 fixture와 내용 hash·기준 버전·허용/금지 작업·관찰 가능한 성공/실패·예산을 고정합니다. 미사용 실패 가설과 근거는 별도 기록합니다. fixture나 기준의 결함을 수정하면 버전을 올리고 이유를 남겨 양쪽 조건을 다시 실행합니다.

실행자에게는 실제 작업 입력·fixture·권한·근거 반환 형식만 줍니다. 기대 정답·실패 가설·다른 실행 결과는 숨깁니다. 평가자는 고정 기준으로 실제 도구 기록과 산출물을 판단합니다. 일반 역할 지침과 필요한 전문 자료는 같은 사례의 양쪽에 동일하게 제공합니다.

## 4. 사용·미사용 비교와 실제 로딩

- 실제 runtime 구현 뒤 현재 작업 파일의 경로·내용 hash를 고정하고 실행 중 변경하지 않습니다. 설치 cache를 대상 원본으로 대체하지 않습니다.
- 같은 모델·설정·도구·권한·요청·fixture·실행 예산으로 독립적인 새 실행을 준비합니다. Codex에서는 조건마다 새 프로세스·격리 workspace·새 HOME/CODEX_HOME·빈 사용자 설정을 사용하고 공통 필수 지침과 허용된 인증은 동일하게 유지합니다.
- 사용 조건에는 `.agents/skills/verify` 임시 심링크로 고정한 실제 skill과 리소스를 연결합니다. native discovery를 유지하고 실행자가 직접 선택·본문 읽기를 수행하게 합니다. 미사용 조건은 링크를 생략하고 상위·사용자·plugin·동명 경로에서 대상이 노출되지 않는지 확인합니다.
- metadata 발견, 선택, 실제 SKILL.md·리소스 읽기, 방법 선택, 실제 실행·판정을 별도로 기록합니다. 설치·심링크·호출 문자열만으로 로딩 성공을 판정하지 않습니다.
- 자동 선택은 일반 요청으로 확인하고 비대상 요청의 오선택도 확인합니다. 명시 호출은 실제 발견된 native 식별자를 사용합니다. plugin-scoped `$quality:verify` 호출은 구현·등록 후 별도의 패키징 통합 검사로 확인하며 로컬 심링크와 혼동하지 않습니다.
- 본문 직접 주입은 보조 실험일 뿐 native 로딩 검증을 대체하지 않습니다. 동등한 환경·격리·로딩 근거를 확보하지 못하면 비교 무효나 미완료로 보고합니다.
- 외부 서비스는 가능한 한 격리 fixture로 대체하고 실제 필요한 권한·비용·전송 범위를 보존합니다. 시각 도구나 실행 수단이 없으면 해당 실제 검증은 미실행이며 source 검사로 대체 성공시키지 않습니다.
- 종료 후 이번 실행에서 만든 임시 링크만 제거하고 원본·기존 설정은 보존합니다. 같은 snapshot과 기준으로 위반·회귀를 대조합니다.

## 5. 판정과 후속 검증

각 실행의 계약 충족을 먼저 판단한 뒤 양쪽 결과를 비교합니다. 미사용 실패/사용 성공은 해당 사례의 개선 근거, 양쪽 성공은 충족 근거이며 추가 효과는 미확인, 양쪽 실패는 해결 효과 미확인, 미사용 성공/사용 실패는 회귀 후보입니다.

일반·실패 가설 사례와 양쪽 실행, 실제 로딩·근거를 확보해야 비교 완료를 주장합니다. 중요한 권한 위반이나 거짓 통과를 평균 점수로 상쇄하지 않습니다. 단회 성공은 일반 성능·안정성을 입증하지 않습니다.

지침에 기인한 위반을 확인하면 계약과 runtime을 수정하고 원래 사례와 영향받는 일반 사례를 같은 기준으로 재검증합니다. 도구·fixture·관찰·로딩 문제는 산출물/skill 실패와 분리합니다. 추가 검사와 반복 수는 실제 불확실성·위험·실패 증거에 맞춥니다.
