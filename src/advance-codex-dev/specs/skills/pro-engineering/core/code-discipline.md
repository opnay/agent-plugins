# Code Discipline Contract

## 책임

이 문서는 코드 작성 방식과 변경 범위 규율을 소유합니다.
`pro-engineering`은 가장 단순한 완전 구현에서 시작하고, 같은 작업 안에서 필요한 수준까지 점진적으로 개선해야 합니다.

## 작은 완전 변경

- 수정은 root cause와 직접 연결된 가장 작은 변경으로 시작합니다.
- "작다"는 incomplete patch를 의미하지 않습니다. 정상 경로, 관련 실패 경로, 필요한 검증까지 포함해야 완전합니다.
- 관련 없는 cleanup, formatting churn, 구조 재배치는 같은 변경에 섞지 않습니다.
- public contract를 바꿔야 한다면 호출부, 문서, 테스트, migration 영향을 함께 다룹니다.
- 변경이 책임 경계를 건드리면 가까워 보이는 파일보다 책임을 소유하는 위치를 우선합니다.
- 작은 변경이라도 호출자와 피호출자, 도메인과 어댑터, 화면과 상태의 경계를 흐릴 수 있으면 먼저 책임 위치를 다시 잡습니다.

## 단순 구현 후 개선

1. 먼저 의도한 동작을 가장 직접적인 방식으로 구현합니다.
2. 중복, 이름, 제어 흐름, 실패 처리, edge case를 확인합니다.
3. 실제로 읽기 어렵거나 위험한 부분만 개선합니다.
4. 개선 후에도 원래 acceptance signal이 유지되는지 확인합니다.

이 순서는 임시 저품질 코드를 남기라는 뜻이 아닙니다.
작동하는 형태를 먼저 만든 뒤, 같은 턴에서 필요한 품질까지 끌어올리라는 의미입니다.

## 변경 범위

- 소유권 경계를 지킵니다.
- 주변 파일이 이미 바뀌어 있으면 사용자 변경으로 간주하고 되돌리지 않습니다.
- 같은 파일에서 충돌하는 맥락이 있으면 현재 코드 상태에 맞춰 적응합니다.
- 불필요한 rename, reformat, import 정렬은 변경 원인을 흐릴 수 있으므로 피합니다.

## 코드 품질 기준

- 이름은 domain concept, state, failure case를 정확히 드러내야 합니다.
- 조건문은 읽는 사람이 어떤 경우가 처리되는지 추적할 수 있어야 합니다.
- 오류 처리는 원인과 회복 가능성을 구분해야 합니다.
- comment는 코드만으로 알 수 없는 제약, 판단 이유, 실패 처리 의도를 설명할 때만 사용합니다.
- edge case는 발견된 실패 메커니즘이나 명시된 계약과 관련될 때 처리합니다.

## 금지되는 작성 방식

- 근본 원인 없이 symptom만 덮는 patch
- 책임 경계가 애매한데도 가까운 파일에만 넣는 patch
- 실패를 삼키는 대체 동작
- 테스트를 통과시키기 위한 assertion 약화
- 미래 요구를 상상한 speculative hardening
- 사용자 변경 또는 무관한 worktree 변경 되돌리기
