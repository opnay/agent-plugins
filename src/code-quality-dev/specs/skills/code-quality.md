## 사용자 스펙 의도

- `code-quality` 스킬은 production code를 정확하고 이해하기 쉬우며 안전하게 변경·검증할 수 있게 작성, 수정, 리팩터링, 검토하게 한다.
- 이 스킬은 코드가 깔끔해 보이는지만 평가하지 않고 요구사항과 실제 동작, 변경 안전성, 복잡도, 오류와 경계값, 테스트, 저장소 관례, 기존 기능, 재사용 적합성, 의존성 필요성, 성능·보안·호환성·데이터 무결성·운영 안정성을 함께 판단한다.
- 좋은 코드는 모든 것을 직접 구현하지 않는다. 저장소 내부 구현, 프레임워크와 시스템 API, 표준 라이브러리, 기존 의존성 및 유틸리티를 먼저 탐색하고 의미와 계약 및 장기 비용을 평가한 뒤 재사용 또는 직접 구현을 선택한다.
- 특정 서적이나 "클린 코드" 교리를 기계적으로 적용하지 않는다.
- 문서 작성, 번역, generated/vendor code, formatting-only 변경에는 명시 요청이 없는 한 호출되지 않는다.
- 시나리오 테스트 결과에 따라 pure naming-only, style-only, formatting-only 요청은 readability라는 단어와 겹치더라도 기본적으로 호출하지 않는다. `명시 요청`은 단순히 사용자가 포맷이나 이름 변경을 분명히 요청했다는 뜻이 아니라 `$code-quality` 호출 또는 code-quality/risk/correctness/compatibility/security 검토를 명시한 경우를 뜻한다.

# code-quality 스킬 스펙

## 목적

`code-quality`는 production code 작업에서 정확성, 명확성, 유지보수성, 테스트 가능성, 견고성, 적절한 재사용, 단순성을 균형 있게 판단하게 하는 skill입니다.

## 경계

- 포함:
  - 구현, 버그 수정, 리팩터링, 테스트 추가
  - architecture와 dependency decision
  - 기존 도메인 기능, 프레임워크/시스템 API, 표준 라이브러리, 설치된 의존성, 내부 패키지, 기존 유틸리티 조사와 적합성 판단
  - 위험 중심 code review
  - 변경 후 관련 검증 실행과 보고
- 제외:
  - prose-only 작업
  - 번역
  - `$code-quality` 호출이나 code-quality 검토 요청이 없는 generated/vendor code 직접 수정
  - formatting-only, style-only, naming-only 변경
  - 임의의 함수 길이, 매개변수 수, 패턴 적용 같은 절대 규칙

## 처리하려는 작업 형태

- 코드 변경 전에 저장소 맥락, existing contract, 테스트, 호출부, 의존 대상을 확인해야 하는 작업
- 재사용과 직접 구현 사이의 tradeoff가 있는 작업
- 새 외부 의존성 추가 여부를 보안, 라이선스, 호환성, 장기 비용까지 검토해야 하는 작업
- 리뷰에서 실제 실패 가능성과 최소 수정 방향을 제시해야 하는 작업
- generated/vendor 산출물 자체를 직접 고치는 작업이 아니라 wrapper, schema/source fix, rollback/risk strategy, security/compatibility review처럼 code-quality 판단을 수행하는 작업
- 문서 안의 code snippet, command, SQL, configuration 예시가 실제 API 호환성, 보안, 데이터 손실, 운영 위험을 만들 수 있는지 검토하는 작업

## 엔트리포인트 / 대표 표면

- 대표 표면: `skills/code-quality/SKILL.md`
- 상세 기준: `skills/code-quality/references/*.md`
- 호출 방식: 명시 `$code-quality-dev:code-quality` 또는 production code 구현·수정·검토 요청의 암시 호출

## 핵심 처리 계약

- 작업 전 요구사항, 변경 대상, 인접 코드, 테스트, 호출자, 공개 API, 호환성, 저장소 개발 규칙, 검증 명령을 조사합니다.
- 새 구현이나 의존성을 만들기 전에 기존 도메인 기능, 공용 모듈, 프레임워크/시스템 API, 표준 라이브러리, 설치된 외부 의존성, 내부 패키지, 기존 유틸리티를 조사합니다.
- 재사용 후보는 이름이나 출처가 아니라 의미, 계약, 오류 모델, 경계 조건, 소유권, 변경 주기, 결합도, 성능, 보안, 라이선스, 배포, 교체 비용을 기준으로 판단합니다.
- 가장 작은 일관된 설계를 선택하되, 단순함을 줄 수가 적은 것과 동일시하지 않습니다.
- 정확성, 보안, 호환성, 데이터 무결성, 운영 안정성을 코드 미관보다 우선합니다.
- 변경 후 관련 테스트, 타입 검사, 린트, 포맷 검사, 빌드, 통합 검증 중 가능한 범위의 검증을 수행합니다.
- 완료 전 diff를 자체 검토해 요구 충족, 기존 동작 보존, 실패 경로, 이름과 구조, 불필요한 추상화, 보안·성능·동시성·데이터 무결성 위험을 확인합니다.
- 사용자가 단순히 이름, 문체, 들여쓰기, 줄바꿈, 표 정렬, 코드블록 언어 태그처럼 동작·계약·위험 검토가 없는 변경만 요청하면 이 skill은 적용하지 않습니다.
- generated/vendor code 예외는 좁게 적용합니다. `$code-quality`를 직접 호출했거나 보안·호환성·운영 위험 검토, wrapper/schema/source 대안, 임시 patch 위험 평가가 명시된 경우에만 다룹니다.

## 판단 우선순위

1. 사용자 요구사항과 보존해야 하는 동작
2. 정확성, 데이터 무결성, 보안, 공개 API 및 저장 데이터 호환성
3. 저장소 `AGENTS.md`, README, 설계 문서, lint/format/type/test 설정
4. 저장소가 명시적으로 채택한 공용 모듈, 프레임워크 사용 방식, 의존성 정책
5. 현재 코드베이스에서 일관되게 사용되는 구조와 관례
6. 언어와 프레임워크의 일반 관용 표현
7. 이 skill의 일반 코드 품질 원칙

상위 규칙이 명백한 버그, 보안 문제, 데이터 손실, 심각한 운영 위험을 만들 수 있으면 위험을 명시합니다.

## 검토 질문

- 요구사항과 실제 동작이 정확한가?
- 다른 개발자가 안전하게 이해하고 변경할 수 있는가?
- 복잡도가 문제의 본질보다 커지지 않았는가?
- 오류, 경계값, 실패 상황이 명시적으로 처리되는가?
- 테스트가 중요한 동작과 회귀 위험을 검증하는가?
- 저장소 구조와 관례를 존중하는가?
- 이미 존재하는 적합한 기능을 모르고 다시 구현하지 않았는가?
- 재사용이나 공통화가 잘못된 결합을 만들지 않는가?
- 새로운 외부 의존성이 실제로 필요한가?
- 성능, 보안, 호환성, 데이터 무결성, 운영 안정성이 코드 미관보다 우선됐는가?

## 독립성 원칙

- 이 skill은 독립 실행 가능성을 강제합니다.
- 이유: 생산 코드 품질 판단은 특정 sibling skill의 숨은 문맥 없이도 작동해야 하며, 설치 후 runtime 표면만으로 구현·리뷰 절차를 수행할 수 있어야 합니다.

## 확장 원칙

- 새로운 절대 규칙을 늘리기보다 적용 조건, 예외, 실패 조건을 함께 설명합니다.
- 반복되는 긴 판단 기준은 `SKILL.md`에 넣지 않고 reference로 분리합니다.
- deterministic automation이 필요한 반복 작업이 확인되기 전까지 script를 추가하지 않습니다.
