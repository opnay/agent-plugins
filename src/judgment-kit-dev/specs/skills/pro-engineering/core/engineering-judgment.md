# Engineering Judgment Contract

## 책임

이 문서는 기술 판단 기준을 소유합니다.
`pro-engineering`은 코드를 "돌아가게" 만드는 것에서 멈추지 않고, 변경 범위와 유지보수 비용, 실패 모드, 검증 가능성을 함께 판단해야 합니다.

## 기존 패턴 우선

- 저장소의 기존 구조, 도우미, 이름 규칙, 오류 처리, 테스트 스타일을 먼저 확인합니다.
- 새 패턴은 기존 패턴으로 목표를 달성할 수 없거나, 기존 패턴이 문제의 일부라는 근거가 있을 때만 도입합니다.
- 같은 기능을 두 번째 방식으로 구현하는 변경은 장기 유지보수 비용을 늘리므로 명시적 이유가 필요합니다.

## 소유권 경계

- 새 동작, 규칙, 상태, 검증, 대체 동작이 책임 위치를 옮기거나, 드러내거나, 중복시키거나, 흐릴 수 있을 때 소유권 경계를 확인합니다.
- 책임 위치는 호출자, 피호출자, 도메인 계층, 어댑터, 저장소, 화면, 테스트 하네스 중 어디가 계약을 가장 잘 소유하는지 기준으로 정합니다.
- 가까운 파일에 수정하는 것과 올바른 계층에 책임을 두는 것은 다를 수 있으므로, 경계가 애매할 때만 멈춰서 확인합니다.
- 호출자가 피호출자의 내부 상태, 저장 순서, 캐시 정책, 실패 복구 방식을 알게 되면 경계 누수 신호로 봅니다.
- 소유권이 불명확하면 구현 전에 계약 이름, 호출 방향, 상태 소유자, 실패 책임을 먼저 좁힙니다.
- 검증은 가장 늦지 않게 실패를 잡고, 가장 중복 없이 계약을 보장하는 경계에 둡니다.
- 대체 동작은 제품 동작인지 장애 은폐인지 구분하고, 책임 소유자가 관측 가능하게 만들어야 합니다.
- 공통 도우미가 여러 계층의 결정을 섞기 시작하면, 책임을 명확히 하는지 먼저 확인합니다.

## 구현 로직 책임

- 도메인, 조정, 기반은 구현 로직의 책임과 데이터 흐름을 읽기 위한 렌즈입니다. 모든 코드베이스에 세 개의 물리 계층, 폴더, 파일을 만들라는 구조 규칙이 아닙니다.
- 도메인 책임은 제품 정책, 의미 있는 수치, 불변식, 자격 조건, 상태 전이를 소유합니다. HTTP, 데이터베이스 형식, JSON 표현, 화면 상태 같은 외부 세부를 알게 되면 경계 누수로 봅니다.
- 조정 책임은 외부 입력과 도메인 입력 사이의 변환, 호출 순서, 결과와 실패의 번역을 소유합니다. 도메인과 기반 기능을 연결할 수 있지만 임계값, 자격 조건, 기본 정책을 새로 결정하지 않습니다.
- 기반 책임은 파싱, 포매팅, 컬렉션, 시간, URL 처리처럼 제품 의미에 중립적인 유틸리티와 원시 기능을 제공합니다. 제품 API 경로, 도메인 상태, 화면 타입을 알게 되면 일반 기반 책임으로 보지 않습니다.
- 어댑터, 저장소, 인프라 코드가 기술적으로 아래에 있다는 이유만으로 기반 책임이 되지는 않습니다. 제품 계약이나 외부 표현을 아는 경계는 어댑터·저장소 소유권을 유지하고, 그 안의 도메인 중립적인 기계 동작만 기반 책임으로 재사용할 수 있습니다.
- 대표 데이터 흐름은 `외부 또는 화면 입력 → 조정 → 도메인 결정과 상태 전이 → 조정의 결과·실패 번역 → 외부 또는 화면 출력`입니다. 기반 책임은 필요한 중립 기능을 제공하되 도메인, 조정, 화면을 역으로 의존하지 않습니다.
- 작은 응집 단위가 여러 책임을 함께 수행해도 명확성과 검증 가능성이 유지된다면 즉시 물리적으로 나누지 않습니다. 책임 누수나 변경 이유가 실제로 갈릴 때 분리를 검토합니다.

## 모듈과 재사용 경계

- 기본값은 가장 작은 응집된 구현을 책임 소유자 가까이에 두는 것입니다. 한 소유자만 사용하는 작은 도메인 규칙이나 수치는 매개변수화할 수 있다는 이유만으로 추출하지 않습니다.
- 새 경계가 현재의 유지보수 또는 검증 비용을 낮추는 이익이 간접성, 의존성, 매개변수 전달, 추가 조정, 호환성 비용보다 클 때만 분리합니다.
- 코드 줄 수나 비즈니스 규칙의 크기보다 책임, 변경 이유, 데이터 흐름, 소유권이 갈리는지를 분리 기준으로 봅니다.
- 분리된 경계는 입력, 출력, 오류, 부수 효과, 호출 방향을 명시할 수 있고 독립적으로 검증할 수 있어야 합니다.
- 여러 실제 소비자가 공유하는 안정된 규칙은 I/O와 orchestration에서 분리하되, 규칙을 정의하는 도메인 소유자의 모듈에 둡니다.
- 소비자 간 동작이 다르면 이를 중복으로 단정하지 말고 하나의 정책인지 의도된 차이인지 먼저 확인합니다. 제품 결정이 없으면 공통 계약을 임의로 확정하지 않습니다.
- 별도 package나 shared library는 소비자, 배포, 버전, 호환성 책임이 실제로 독립될 때만 선택합니다. 같은 소유자와 배포 단위 안에서는 내부 모듈을 우선합니다.
- 기반 책임은 여러 현재 소비자가 같은 도메인 중립 계약을 사용할 때 재사용할 수 있습니다. `utils`라는 이름이나 합칠 수 있다는 사실만으로 서로 다른 원시 기능을 한 모듈에 모으지 않습니다.
- 응집된 제품 정책을 작아 보이게 하거나 미래 재사용 가능성만 대비하려고 interface, layer, package를 늘리지 않습니다.
- 처리 단계를 나누면 각 단계의 계약이 독립적이어야 하며, 분리 때문에 transaction, invariant, ordering이 깨지면 안 됩니다.

## 추상화 판단

- 추상화는 코드가 멋져 보이게 하기 위한 장치가 아닙니다.
- 실제 중복을 줄이거나, 복잡한 규칙을 한 곳으로 모으거나, 이미 존재하는 설계와 맞을 때만 추가합니다.
- 한 번만 쓰는 함수나 wrapper는 테스트 가능성, 의미 부여, 실패 경계 분리 같은 실질적 이점이 있어야 합니다.
- 미래 가능성만으로 추상화를 추가하지 않습니다.

## 계약 명시성

- 입력, 출력, 오류, 부수 효과, 소유권 경계가 코드나 테스트에서 드러나야 합니다.
- 금지 목록을 늘리기 전에 허용되는 입력, 상태, 전이, 효과, 실패 조건을 먼저 정의합니다.
- 예외나 차단 조건은 허용 계약을 보완하는 좁은 방어선으로 둡니다. 예외가 계약보다 커지면 계약 소유자나 데이터 모델을 다시 확인합니다.
- 알 수 없는 값은 조용히 통과시키지 말고, 허용 계약을 만족하는지 검증하거나 명시적 실패로 보냅니다.
- 문자열, JSON, 외부 입력처럼 깨지기 쉬운 경계는 가능한 구조화된 파서, 검증, 타입, 명시적 schema로 다룹니다.
- 대체 동작이 필요하면 어떤 조건에서 동작하는지, 실패를 숨기지 않는지 확인합니다.
- 조용히 실패를 삼키는 대체 동작은 운영자가 문제를 발견하기 어렵게 만들기 때문에 기본 선택이 아닙니다.

## 리스크 배수

다음 요소가 있으면 더 강한 증거와 검증이 필요합니다.

- concurrency, async ordering, caching, time, timezone
- randomness, retry, timeout, backoff
- external service, network, filesystem, process boundary
- auth, permission, data migration, destructive action
- shared library, public API, broad UI workflow

## 사용자 입력이 필요한 경우

다음은 추측으로 밀어붙이지 않고 사용자 확인이 필요한 판단입니다.

- 제품 의도나 정책 선택이 여러 가지로 가능할 때
- 위험 허용 범위나 배포 전략이 결과를 바꿀 때
- 로컬 증거만으로 확인할 수 없는 외부 상태가 핵심일 때
- 변경이 public contract를 깨거나 migration을 요구할 때

확인이 필요하지 않은 경우에는 로컬 증거를 기준으로 계속 진행합니다.
