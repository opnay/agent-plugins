# Project Design Context

Use this contract to locate and apply project design knowledge. It does not require running another skill first.

## Locate the Owner

1. Identify the target project and whether the request permits reading, artifact changes, or durable rule updates.
2. Read applicable project instructions and supplied design material. Follow the existing documentation index to the owned design or brand guidance.
3. Inspect relevant tokens, components, patterns, and representative artifacts only as needed. Use scoped searches; do not inventory unrelated projects.
4. Distinguish explicit current user decisions and adopted rules from implementation observations, experiments, and assumptions.

When context is missing, state a narrow assumption and continue work that it does not materially change. Ask only when an unresolved choice would substantially change the requested outcome.

## Apply the Right Scope

- Reuse adopted rules whose project, medium, screen group, component, or state matches the task.
- Check direction, base choices, and related patterns. Preserve meaning when reusing terms, colors, motifs, layout, and interaction.
- Existing implementation is evidence, not automatic policy. If documentation and implementation disagree, identify the difference and its effect before choosing a task-scoped resolution.
- Apply explicit user changes within their stated scope. If they conflict with essential readability, accessibility, truthful state, or functional meaning, explain the conflict and offer a workable alternative.
- Label unconfirmed extensions as candidates. Do not silently turn a one-off workaround into a project-wide rule.

## Preserve Knowledge Appropriately

Use existing design documentation and its organization. If rule writing is authorized and no owned location exists, default to `docs/design.md` in the target project. Inspect an existing file before editing it; preserve unrelated material.

For an ordinary design task, identify reusable decisions in the handoff without assuming authority to create durable documentation. For a request to establish, record, or update rules, update the relevant owned entries and use the project's existing documentation navigation to make them discoverable.

Keep project decisions in that project, not in installed plugin files, other projects, or an external wiki. Never imply a proposal was saved when it was only described.

For each affected rule, distinguish application, extension, or change; retain its context, rationale, evidence, status, and any replacement relationship. Keep unresolved conflicts visible rather than overwriting an adopted rule without a basis.
