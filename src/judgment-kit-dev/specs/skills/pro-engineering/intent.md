## 사용자 스펙 의도

- 엔지니어링 가이드를 단순한 코딩 스타일 목록이 아니라 문제 해결 논리 중심으로 제공하고 싶다.
- 코드 작성 시 엔지니어가 알아야 할 논리, 기술 판단, 코드 작성 방법, 원인 분석, 검증 방법을 다루고 싶다.
- 구체 언어/프레임워크 레시피보다 실제 작업 중 판단 기준으로 사용할 수 있는 원칙을 원한다.
- `pro-engineering` 스펙은 단일 파일에 모든 내용을 압축하지 않고, 폴더 기반 구조에서 각 세부 책임을 자세히 설명해야 한다.
- 자료조사, 구현 범위 조정, 문제 공간 파악처럼 직접 코딩 전 단계에서는 넓은 범위를 탐색하고, 실제 구현 단계에서는 코드를 좁은 범위로 집중해서 봐야 한다.
- blocklist 대응보다 allowlist 대응을 선호하는 기준을 `pro-engineering`의 기존 축과 어울리게 다듬고 싶다.
- 조건문과 관련해 early-return 패턴 선호도 추가하고 싶다.
- 큰 구현은 파일이나 계층별 미완성 조각이 아니라 독립적으로 검증 가능한 완결 결과로 나누고 싶다.
- 코드 분리는 책임, 변경 이유, 데이터 흐름, 명시적 계약을 기준으로 판단하고, 실제로 공유되는 안정된 규칙만 재사용 경계로 두며 미래 가능성만으로 추상화하지 않게 하고 싶다.
- 구현 로직을 제품 판단을 소유하는 책임, 경계를 연결하는 책임, 도메인에 중립적인 기반 책임으로 구분해 보되 이를 고정된 물리 계층이나 폴더 구조로 강제하지 않고 싶다.
- 작은 단일 소유자 규칙은 먼저 단순하고 가까운 곳에 유지하고, 분리가 현재의 유지보수와 검증 비용을 실제로 낮출 때만 경계를 만들고 싶다.
- 경계 연결 책임이 제품 정책을 대신 결정하거나 기반 책임이 제품·화면 타입에 의존하는 역방향 결합을 피하고 싶다.
