# verify 스킬 스펙

사용자 스펙 의도는 [intent.md](intent.md)가 소유합니다.

## 목적

산출물의 목적·특성·위험에서 검증할 품질 축과 판정 기준을 도출하고, 적합한 검증을 실제로 수행해 근거 있는 판단을 제공합니다. 분야별 전문가 역할이나 결과 취합으로 범위를 한정하지 않습니다.

## 경계와 선택 기준

- 선택: 산출물의 적합성·완성도·일관성·신뢰성 등을 판단하거나 그 판단에 필요한 절차를 설계해야 할 때 사용합니다. 특정 분야·파일 형식·자동 테스트 가능 여부로 제한하지 않습니다.
- 비목표: 산출물 제작·수정, 제품 목표 변경, 설치·접근·외부 변경 권한의 확장, 고정 검사 수·점수·통과율 부과, 근거 없는 인증·출시 승인.
- 일반 작업을 이 skill의 필수 전체 감사로 확대하지 않습니다. 검증 축·방법·깊이는 요청과 실제 특성·불확실성·영향·비용에 맞춥니다.
- 설계·계획 요청은 검증 계획을 반환합니다. 실행을 요청받았거나 작업 범위에서 필요한 검증만 수행하고 계획을 실행 결과로 표현하지 않습니다.

## 입력과 대표 표면

- 식별자: `$quality:verify`. runtime 대상: `capabilities/quality/skills/verify/SKILL.md`.
- 입력: 산출물 또는 접근 경로, 목적·소비자·사용 맥락, 원본 요구와 제약, 관련 규칙·전문 기준, 대상 버전·환경, 허용 작업·도구·권한, 필요한 판단·출력 형식.
- 입력은 모두 고정 필수 필드가 아닙니다. 산출물과 자료를 먼저 확인해 추론 가능한 맥락을 확보합니다. 판단·범위·권한을 실질적으로 바꾸는 공백만 질문하고 독립적으로 가능한 검증은 진행합니다.
- 대상은 작업에 맞는 수준으로 식별합니다. commit·빌드·파일 버전·화면 상태·데이터 기준일 등 실제 판정을 재확인할 식별 근거를 남기되 모든 작업에 hash나 별도 장부를 강제하지 않습니다.

## 핵심 처리 계약

1. **대상 이해**: 실제 산출물과 원본 기준을 읽거나 관찰합니다. 목적·환경·구성·소비자·보호할 계약·변경 범위를 확인합니다. 작성자의 설명·성공 주장과 직접 관찰을 구분합니다.
2. **검증 축 도출**: 산출물의 성질·주장·상호관계·변경 영향·실패 가능성에서 판단해야 할 사항을 도출합니다. 분야 이름으로 검사 범위를 고정하지 않습니다. 새로운 특성이면 새 검증 축을 정의할 수 있습니다.
3. **기준과 근거 설정**: 각 중요 주장에 무엇을 충족해야 하는지, 어떤 근거로 판정할지 정합니다. 명시 요구·소유 계약·확인한 표준·관찰 사실과 목적에서 도출한 기준·가정·미해결 정책을 구분합니다. 기준을 확보할 수 없는 중요한 판단은 확정하지 않습니다.
4. **방법 선택**: 검사할 주장·위험에 적합한 절차와 입력·상태·경계·관찰 대상을 정합니다. 가장 적은 비용으로 주장을 직접 확인하는 방법부터 선택하고, 도달하지 못하는 위험에만 별도 방법을 추가합니다.
5. **실행과 근거 확보**: 허용된 검증을 수행하고 실제 결과를 기준과 대조합니다. 검사 목록·도구 호출·반환 코드·다른 agent의 결론만으로 의미 있는 결과를 대신하지 않습니다. 원래 계약을 위반하면 관측 결과가 달라지는 검사인지 확인합니다.
6. **판정과 재검증**: 결함·충족·불확실성을 근거 강도에 맞춰 보고합니다. 실패를 소유 부분과 연결하고, 수정이 별도로 허용되면 영향받는 주장과 관련 회귀를 재검증합니다. 기준을 사후 완화해 통과시키지 않습니다.

## 품질 축과 방법의 관계

| 산출물에서 발견한 특성 예시 | 가능한 기준·검증 방법 예시 |
| --- | --- |
| 동작·상태 전이·실패와 복구 | 행동 계약 대조, 실제 경로 실행, 경계·예외·회귀 검사 |
| 구조·소유권·변경 용이성·호환성 | source·의존·책임 검토, 정적 분석, 실제 소비자와 변경 영향 확인 |
| 시각·공간·지각·조작 | 실제 렌더와 산출물 관찰, 크기·상태·콘텐츠별 확인, 디자인·접근성 기준 대조 |
| 주장·논리·의사결정·전달력 | 원본 요구·사실 대조, 논리·일관성·반례·독자 과업 검토 |
| 수치·데이터·측정 | 독립 재계산, 표본·누락·정의·기간·오차·재현성 확인 |
| 근거·출처·최신성·추적 가능성 | 원본 확인, 주장별 지지 여부·독립성·반대 근거·적용 범위 대조 |
| 권한·정보·외부 시스템·운영 | 위협·흐름·권한·장애·복구 계약 대조와 허용된 실제 경로 확인 |

표는 선택 예시이며 전체 범위·필수 순서·분야별 검사표가 아닙니다. 같은 산출물에 여러 축이 적용될 수 있고 새로운 축도 추가할 수 있습니다. 전문 기법이 필요하면 사용 가능한 기준·자료·도구·역할 지식을 확인합니다. 부족한 전문 지식이나 접근 권한을 skill 설치로 충족됐다고 보지 않습니다.

## 실행·증거·변경 통제

- 원본 기준과 독립적으로 대조할 수 있는 실제 결과를 우선합니다. 산출물이 만든 기대값·같은 주장의 반복·작성자의 통과 선언을 독립 근거로 세지 않습니다.
- 정적 근거와 실행·시각·통합 근거가 각각 입증하는 범위를 구분합니다. 필요한 관찰을 할 수 없으면 다른 증거로 무엇까지 판단할 수 있는지 밝힙니다.
- 사실과 기술적 결함, 취향·개선 제안, 검증되지 않은 가설을 구분합니다. 해석이나 주관적 기준도 근거·맥락·한계를 밝히며 객관적 실패로 포장하지 않습니다.
- snapshot·환경·원본이 바뀌면 영향받은 근거의 유효성을 재평가합니다. 변경 전 결과를 새 버전의 통과 근거로 재사용하지 않습니다.
- 검토 요청은 산출물을 직접 수정하는 권한이 아닙니다. 검증용 임시 실행·fixture·출력은 기존 허용 범위를 따릅니다. 외부 변경·비용·배포·자격 증명 접근 권한을 새로 만들지 않습니다.
- 다른 agent가 반환한 판단은 관찰 자료입니다. 중요 판단은 실제 산출물·실행 근거·원본 기준으로 재확인합니다. 별도 agent만으로 독립 검토가 입증됐다고 주장하지 않습니다.

## 판정과 출력 계약

각 중요한 검증 항목은 대상 범위·기준과 출처·방법·실제 근거·판정·남은 불확실성을 연결합니다. 문장·목록·표 중 작업에 맞는 가장 간단한 형식을 사용하며 장부·점수·고정 템플릿을 강제하지 않습니다.

- `pass`: 식별한 범위·기준을 충족한다는 충분한 근거가 있습니다.
- `fail`: 근거 있는 기준 위반을 실제로 확인했습니다. 위치·상태·재현 조건과 영향을 제시합니다.
- `inconclusive`: 관찰·기준·전문 근거가 부족하거나 충돌해 판단할 수 없습니다.
- `not-run`: 실행하지 않았습니다. 이유와 판단에 미치는 영향을 제시합니다. 도구·환경 오류와 대상 결함을 구분합니다.

전체 결과는 **확인된 결함**, **선택한 범위 충족**, **판정 유보**를 구분합니다. 중요 결함은 다른 성공으로 상쇄하지 않습니다. 필수·중요 검증이 미실행이거나 불충분하면 전체 통과를 선언하지 않습니다. 그 밖의 위험·제외·권고 사항은 해당 범위와 이유를 밝힙니다. 특정 검사 통과를 전체 분야의 무결성으로 확대하지 않습니다.

산출물의 결함과 검증 절차·환경의 결함을 구분하고, 다음에 필요한 근거·소유 역할·재검증을 제시합니다. 검증 계획 요청에는 실행 전제·방법·관찰할 근거·성공/실패 조건·미해결 사항을 반환하며 실행한 것으로 표시하지 않습니다.

## 종료와 범위 재평가

- 선택한 범위의 중요한 주장이 근거로 판정됐고 남은 위험·미검증의 영향이 설명되면 종료할 수 있습니다. 모든 가능한 품질 축을 끝없이 조사하지 않습니다.
- 원본 요청·필수 수용 조건을 검증 범위에서 유지합니다. 중요한 조건을 임의로 제외하거나 범위를 줄여 완료를 선언하지 않습니다. 제한으로 확인하지 못한 조건은 이유·영향과 함께 미완료로 반환합니다.
- 새 근거가 중요한 누락이나 검증 가정의 오류를 드러내면 해당 범위와 방법을 보완합니다. 추가 검사가 같은 근거만 반복하면 확대하지 않습니다.
- 실행 조건·권한·시간·비용 제한으로 필요한 검증을 마칠 수 없으면 부분 결과와 미완료 범위·이유를 반환합니다. 제한을 통과 판정으로 바꾸지 않습니다.
- 요구나 기준의 오류가 발견되면 변경 이유·근거·영향을 밝히고 권한 안에서 조정합니다. 목표·정책·권한을 바꾸는 결정은 소유자에게 돌려줍니다.

## 독립성과 관계

- runtime은 본문과 실제 번들 리소스만으로 실행 계약을 이해할 수 있어야 합니다. 특정 역할 plugin·개발 spec·orcat·오케스트레이터를 숨은 선행 조건으로 두지 않습니다.
- 전문 지식은 현재 산출물의 검증 기준을 제공하며 이 skill이 모든 전문 기준을 소유하거나 재정의하지 않습니다.
- 오케스트레이션은 실행 배치, 이 skill은 검증 절차를 소유합니다. 위임받은 검증자는 별도 spawn 권한을 전제하지 않고 받은 범위를 수행합니다.
- 제작·수정·release 승인은 각 작업의 권한을 유지합니다. 이 skill이 통과 여부를 보고하는 것과 외부 조치를 승인하는 것은 다릅니다.

## 검토 질문과 확장 원칙

- 산출물의 실제 특성에서 축을 도출했으며 분야·검사 목록으로 범위를 닫지 않았습니까?
- 기준의 출처·가정·정책 공백과 검증 방법의 한계를 밝혔습니까?
- 계획·설치·호출·작성자 주장 대신 실제 산출물과 의미 있는 결과를 확인했습니까?
- 결함과 취향, 환경 실패와 대상 실패, 관찰과 추론을 구분했습니까?
- 중요한 미검증·snapshot 변경·권한 제한을 숨기지 않았습니까?
- 같은 기준·절차를 분야별 sibling skill로 복제하지 않고 새 유형도 같은 계약에 연결합니까?

비교 검증 기준과 사례 설계는 [plugin 검증 계획](../../validation-plan.md)을 따릅니다. 이 링크는 작성·평가 계약이며 runtime의 필수 입력이 아닙니다.
