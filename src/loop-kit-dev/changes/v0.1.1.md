# loop-kit-dev v0.1.1 변경 스펙

## 변경사항 요약

- `loop-kit`을 `turn-gate` 중심의 좁은 turn-continuity plugin으로 정리한다.
- `flow`를 별도 skill로 추가해 flow boundary, parent/sub-flow candidate, readiness, discovery, flow-local strategy, handoff 판단을 소유하게 한다.
- `turn-gate`는 flow 자체를 정의하지 않고 active turn에서 `flow`를 그대로 적용하며, `flow skill: handoff` 뒤 질문 도구 또는 준비된 self-drive gate로 라우팅한다.
- `turn-gate`의 record, verification, interruption, date 계약은 메인 그래프 노드가 아니라 active turn 복구와 안전한 라우팅을 위한 지원 계약으로 둔다.
- `turn-gate` intent graph는 메인 플로우를 `flow skill` 그룹과 `next-flow gate` 그룹의 루프로 표현한다. `flow skill` 그룹은 `flow skill: interview -> 생략... -> flow skill: handoff`를 포함한다. 질문 도구는 다음 flow 입력 선택을 소유하고, `flow: deep-interview`와 같은 인터뷰 흐름으로 입력을 구체화한다. self-drive는 그래프 노드가 아니라 준비된 sequence gate로 설명한다. `turn-gate`는 `flow` 스킬 내부를 재정의하지 않고 그대로 적용한다.
- 사용자 메시지 노드는 `turn-gate` wrapper 전체가 아니라 wrapper 안의 `flow skill` 그룹으로 직접 연결된다.
- 메인 wrapper 라벨은 `turn-gate / 메인`으로 표시하고, 종료 플로우는 `turn-gate / 메인 -- 모든 시점: 종료 요청 --> 종료 페이즈` 별도 그래프로 분리한다.
- 종료 페이즈는 `작업 중이던 플로우 정리 -> explicit-stop 기록 - active turn 종료` 순서로 처리한다.
- handoff 뒤 질문 도구는 `next-flow gate` 그룹 안에서 `skill reconfigure` 그룹을 거쳐 `질문 도구: 다음 플로우 선택 -> 000-plan.md 업데이트` 순서로 처리한다.
- `skill reconfigure` 그룹은 `flow skill: handoff` 시작점, 세션에서 사용중인 전체 skill 목록 식별, 각 skill 본문 재읽기, 새 active skill set 수용을 소유한다.
- `turn-gate` spec은 현재 의도 다이어그램 `intent.md`, 기존 의도 기록 `intent-legacy.md`, `intent-scenarios/`를 보존하고, 세부 계약을 `contracts/` 중심의 작은 소유 구조로 재작성한다.
- `turn-gate` contract 스펙은 `intent.md` 그래프를 기준으로 wrapper loop, 질문 라우팅, explicit stop, self-drive gate를 소유하고 기록·검증·중단·날짜 처리는 지원 계약으로 둔다.
- self-drive는 별도 skill이 아니라 준비된 finite flow sequence 위에 적용되는 overlay reference로 유지한다.
- verification method를 `clean-context`, `normal`, `not-required`로 구분하고, result status `pass`, `fail`, `blocked`, `insufficient`와 분리한다.
- `request_user_input` abort/cancel은 explicit stop이나 terminal close authority가 아니며, pending question recovery 또는 superseded next-flow routing으로 처리한다.
- `turn-gate` 활성 중 `flow skill: handoff`와 질문 라우팅은 명시적 stop 전까지 terminal/final closeout으로 닫지 않는다.
- `turn-gate` 사용자-facing phase/progress 메시지는 source skill이 소유한 phase prefix로 현재 단계를 드러낸다. `turn-gate`는 `flow` phase label을 재정의하지 않고 적용하며, `next-flow gate`에서는 `[next-flow]`를 소유한다. Artifact/record/command/question option 표면에는 prefix를 전파하지 않는다.
- `flow`는 active flow의 각 phase 시작/종료에서 `000-plan.md` 또는 active flow record 중 어떤 기록 checkpoint가 필요한지 산출한다.
- `flow`와 `turn-gate` spec tree는 현재 계약 중심의 짧은 문서 형식으로 정리하고, runtime 지시와 spec-side fixture의 경계를 더 분명히 한다.
- `flow` spec도 현재 의도 다이어그램을 `intent.md`로 두고, 기존 사용자 의도 기록은 `intent-legacy.md`로 보존한다.
- `flow`는 사용자 메시지 해석 뒤 실제 진행할 메인 플로우 목록을 설계하고, reporting 이후 다음 intake 조건 또는 handoff condition을 산출하는 계약을 명시한다.
- `flow` spec/runtime은 부정형 경계 문장보다 메시지 인터뷰, 플로우 설계, 메인 플로우, handoff의 현재 소유권을 긍정형으로 설명한다.
- `flow` discovery는 외부 workflow 호출이 아니라 flow 내부에 흡수된 intent-first 질문 계약으로 강화한다.
- `flow` checkpoint는 `000-plan.md`에 `skill reconfigure`가 식별한 세션에서 사용중인 전체 skill 목록을 compact하게 드러내고, `turn-gate`는 이를 새 active skill set으로 수용한다.
- `flow` phase model을 `intake -> framing -> preparation -> work -> verification -> reporting`으로 좁혀, 사용자 입력 분석과 flow 설계를 work-readiness preparation에서 분리한다.
- active flow 도중 들어온 사용자 메시지는 일반 lifecycle phase가 아닌 `interruption` entry-only phase로 분류한다.
- flow record template은 기존 섹션을 유지하면서 `Phase Checklist`를 추가해 지나친 lifecycle phase를 복구 가능하게 드러낸다.
- `flow`는 flow plan, active flow record, review 템플릿의 의미와 검토 기준을 소유하고, `turn-gate`는 active turn에서 필요한 적용과 기록 라우팅을 맡는다.
- `flow` runtime은 `templates/plan.md`, `templates/flow-record.md`, `templates/review.md`를 제공한다.
- `000-review.md`는 메인 플로우 그룹 이후, `handoff condition` 직전에 항상 갱신한다. 회고 finding이 없으면 no-finding 결과로 짧게 기록한다.
- self-drive sidecar gate는 inactive/historical sidecar, identity cross-check, no-write boundary, repeat policy, ordinary note, advance confirmation, blocker severity를 직접 구분한다.
- self-drive 문서는 4-loop/8-loop 시나리오 검증에서 드러난 order/endpoint relock, ordinary note 기록 위치, insufficient repair, external blocker recovery, another bounded batch, infinite-to-finite endpoint transition을 직접 설명한다.
- 추가 시나리오 검증에서 드러난 날짜 제외 ambiguity를 반영해 verification enum reconciliation, `not-required` result status, free-form question recovery, natural-language interruption classification, finite sidecar gate recheck를 명시한다.
- turn-gate는 상대 날짜를 기본적으로 시스템 날짜/timezone 기준으로 해석하되, 기록 기반 날짜와 충돌해 target, verification, reporting scope가 바뀌면 사용자 확인으로 라우팅한다.
- 날짜 authority 계약을 `contracts/date-authority.md`로 분리해 시스템 날짜 기본값, 기록 기반 충돌, 절대 날짜 보고 기준을 독립적으로 검토할 수 있게 한다.
- runtime `SKILL.md`는 `intent.md`의 wrapper loop를 기준으로 다시 쓰고, 날짜 authority는 별도 lifecycle로 승격하지 않는다.
- `turn-gate`에 남아 있던 flow-owned 판단을 `flow` 원천 계약에 의존하도록 정리한다. 특히 interruption contract impact, self-drive next identity/handoff, 날짜/target ambiguity, phase checkpoint 판단은 `flow`가 원천이고 `turn-gate`는 적용·기록·라우팅을 소유한다.
- 80개 scenario evaluation partial을 반영해 flow-vs-phase, verification blocker earliest safe phase, post-flow continue, finite self-drive bounded batch refresh, finite blocker recovery, infinite inventory cycle update를 관련 spec/runtime 문서에서 직접 설명한다.

## 변경 상세

### flow skill

- `flow`는 flow boundary, parent flow, finite sub-flow candidate, flow-vs-phase 판단을 소유한다.
- `flow`는 readiness, discovery, ambiguity, review-loop, fix-verify-loop, broad-execution, commit-readiness handoff를 소유한다.
- discovery는 missing field 채우기가 아니라 사용자 intent, scope edge, non-goal, tradeoff, acceptance signal을 압력 테스트해 flow contract를 잠그는 preparation 전략이다.
- `intake`는 사용자 입력 분석, deep interview, 목표/비목표/authority 탐지를 소유하고, `framing`은 flow 분리, 후보/선택 구분, artifact ownership을 소유한다.
- `preparation`은 선택된 active flow의 readiness와 work 진입 가능성 판단으로 좁힌다.
- `sub-flow candidate` 생성은 실행이 아니며, active flow 전환은 `turn-gate` next-flow routing 또는 준비된 self-drive sequence를 통해서만 가능하다.
- 각 active flow phase의 시작과 종료는 current phase, result, required next action, handoff 또는 next-flow 조건을 재구성할 수 있게 plan 또는 flow record 갱신 여부를 판단한다.
- `flow` template spec은 plan을 compact routing card, flow record를 reviewable work unit, review를 retrospective note 표면으로 정의한다.
- `000-plan.md` 갱신이 필요한 경우 `skill reconfigure`가 식별한 세션에서 사용중인 전체 skill 목록을 기록한다.
- flow spec tree는 `소유 범위`, `계약`, `검토 기준` 구조를 사용해 child spec의 역할을 짧게 드러낸다.
- `flow`는 active flow 도중 들어온 새 사용자 메시지가 기존 flow contract를 바꾸는지, 새 foreground flow인지, future candidate인지, inline answer인지 판단하는 contract-impact 기준을 소유한다.
- self-drive나 turn-gate가 다음 flow identity, current flow completion, non-blocked handoff를 확인할 때도 `flow` output contract와 handoff condition을 원천으로 삼는다.
- `flow`는 verification, reporting, evidence repair, blocker recovery가 별도 산출물 없이 새 flow로 승격되지 않도록 flow-vs-phase 기준과 earliest safe phase 라우팅을 소유한다.

### turn-gate skill

- `turn-gate`는 대화 턴 단위의 1급 wrapper로 동작한다.
- 메인 루프는 `flow skill: interview -> flow skill: handoff -> 질문 도구: 다음 플로우 선택 -> flow skill: interview`이다.
- interview에서 handoff까지의 내부 흐름은 `flow`가 소유하므로 `turn-gate` runtime과 spec은 `생략...`으로만 다룬다.
- 질문 도구는 `flow: deep-interview`와 같은 인터뷰 흐름으로 다음 flow 입력을 구체화하고, 충분히 구체화된 입력만 `flow skill: interview`로 되돌린다.
- `next-flow gate`는 매번 `skill reconfigure` 그룹을 수행하고, 질문 결과와 pending/answered question state를 `000-plan.md`에 업데이트한다.
- 사용자-facing phase 시작 또는 의미 있는 진행 메시지는 source skill이 소유한 phase prefix를 사용하고, artifact 본문, record 본문, command output summary, 질문 option label은 prefix 없이 유지한다.
- active turn 중 새 사용자 메시지가 들어오면 `interruption`으로 먼저 처리하고, `inline-answer`, `current-flow-revision`, `background-current-flow`, `reserve-later-analysis`, `supersede-current-flow`, `blocker-question`, `explicit-stop` 중 하나로 라우팅한다.
- `turn-gate`는 interruption, self-drive gate, 날짜 기반 clarification에서 flow-owned 판단을 재정의하지 않고 `flow` decision을 적용해 질문 라우팅을 수행한다.
- 사용자가 현재 turn을 명시적으로 끝내기 전까지 terminal summary로 닫지 않는다.
- record와 verification은 메인 그래프 노드가 아니라 handoff 질문 라우팅을 복구하고 non-pass를 먼저 처리하기 위한 지원 계약이다.
- turn-gate spec tree는 wrapper loop, question routing, self-drive gate, explicit stop을 중심으로 압축하고, scenario fixture는 runtime instruction이 아님을 명확히 한다.

### turn-gate spec reset

- `src/loop-kit-dev/specs/skills/turn-gate/intent.md`는 현재 turn-gate 의도 다이어그램을 소유한다.
- `src/loop-kit-dev/specs/skills/turn-gate/intent-legacy.md`는 기존 사용자 스펙 의도 기록을 보존한다.
- `src/loop-kit-dev/specs/skills/turn-gate/intent-scenarios/`는 regression intent fixtures를 소유한다.
- `src/loop-kit-dev/specs/skills/turn-gate/spec.md`는 index와 boundary map만 소유한다.
- `src/loop-kit-dev/specs/skills/turn-gate/contracts/`는 durable child contract를 소유한다.
- child contract는 wrapper runtime, flow relationship, question routing, self-drive, session records, verification, interruption, date authority로 나누며, 같은 규칙을 여러 spec 파일에 반복하지 않는다.
- `spec.md`는 operational decision table을 갖지 않고, 필수 runtime 동작과 검토 질문 수준의 현재 계약 맵을 유지한다.
- child contract는 각자 소유하는 판단 경계를 충분히 담아 runtime 재생성 기준으로 사용할 수 있어야 한다.

### self-drive

- self-drive는 명시적으로 준비된 finite sequence 또는 infinite loop mode에만 적용된다.
- self-drive sidecar는 mode, goal/objective, current identity, active flow record, next action, endpoint/stop condition, acceptance, verification, approval checkpoints, blocker return condition을 기록해야 한다.
- active self-drive 중 새 사용자 메시지는 explicit stop, approval boundary, scope/non-goal/endpoint/target/order/acceptance change, blocker, status/progress, ordinary note 순서로 해석한다.
- self-drive는 질문 조건을 좁히지만 질문 도구를 비활성화하지 않는다.
- `000-plan.md`가 self-drive inactive이거나 sidecar pointer를 갖지 않으면 sidecar 파일은 historical context이며 continuation authority가 아니다.
- self-drive advance는 current flow verification pass, non-blocked handoff, next flow identity, approval boundary 일치가 모두 확인된 뒤에만 가능하다.
- self-drive template은 mode, active position, next action을 frontmatter로 드러내고, 본문은 goal, 선택적 sequence, ledger, handoff를 유지한다.
- self-drive infinite mode는 큰 todo list를 만들지 않고 `loop_count`, current loop label, `next_action`으로 현재 반복만 기록한다.
- self-drive reporting은 ledger history 보존과 새 material update를 드러내며, blocker impact와 advance confirmation을 template에서 명시한다.
- self-drive finite advance는 repair/recheck를 advance count로 세지 않고, order/endpoint/scope/approval 변경 후 affected phase relock과 sidecar/flow record 갱신을 거친 뒤에만 계속한다.
- self-drive finite는 sequence 완료 뒤 another bounded batch나 inventory cycle 요청이 들어오면 old endpoint에서 이어가지 않고 새 bounded finite cycle로 sidecar를 refresh한다.
- self-drive finite도 external blocker 회복 뒤 plan, sidecar, active flow record를 다시 읽고 endpoint/approval/next identity/verification을 relock한다.
- self-drive infinite advance는 valid continuation 뒤에만 `loop_count`를 증가시키고, 같은 target/cause의 2회 연속 non-pass를 repeated failure로 본다.
- self-drive infinite는 another bounded batch뿐 아니라 another inventory cycle도 endpoint/order update로 직접 처리하며, current loop 포함 여부가 모호하면 clarification으로 라우팅한다.
- verification은 `partial`, `mixed`, `inconclusive` 같은 비표준 결과를 성공으로 승격하지 않고 `pass/fail/blocked/insufficient`로 정합화한다.
- question routing은 visible option과 다른 free-form 답변이 새 작업이면 pending question을 superseded로 처리하고, 선택+note이면 둘 다 기록한다.
- interruption은 "요약만", "나중에", "기억해", "계속" 같은 짧은 자연어를 효과 기준으로 분류한다.

### verification

- 파일 변경, release surface 변경, 다중 파일 계약 변경, prior failure, 사용자 요청 검증, approval-sensitive action에는 `clean-context`가 기본값이다.
- `normal`은 낮은 위험의 no-edit/read-only work에서 source readback, evidence checklist, command/check, 논리 반례 검토로 사용할 수 있다.
- `not-required`는 method일 뿐 성공 결과가 아니며, reason과 residual uncertainty를 기록해야 한다.
- non-pass verification은 endpoint exhaustion이나 next-flow continuation보다 먼저 repair, evidence repair, blocker routing으로 처리한다.

### question routing

- `flow skill: handoff` 뒤 explicit stop이 없다면 next-flow question routing을 연다.
- `request_user_input`이 사용자 interrupt로 abort/cancel되면 turn closure로 보지 않는다.
- abort 이후 다음 사용자 메시지는 pending question answer, superseding new flow request, status/progress question, explicit stop 중 하나로 먼저 해석한다.
- 같은 question tool call을 즉시 반복해 interrupt loop를 만들지 않는다.
- handoff와 next-flow choices는 ongoing conversation channel에 남기며, explicit stop이 source-recorded되기 전에는 final/terminal closeout을 사용하지 않는다.

## 비목표

- `workflow-kit`의 broad workflow taxonomy를 `loop-kit` 안에서 재정의하지 않는다.
- `turn-gate`를 여러 direct loop entrypoint 묶음으로 넓히지 않는다.
- release surface에 `specs/` 또는 `changes/`를 포함하지 않는다.
- readiness, verification, self-drive, 이전 맥락에서 commit/push/PR/publish/release/version-bump 실행 권한을 추론하지 않는다.

## 검증 기준

- dev/release plugin manifests가 valid JSON이고 version `0.1.1`을 유지한다.
- release `loop-kit` surface에는 `specs/`와 `changes/`가 없다.
- dev/release runtime skill surface가 build 후 일치한다.
- `turn-gate` spec tree에는 `intent.md`, `intent-legacy.md`, `intent-scenarios/`, `spec.md`, `contracts/`만 남는다.
- 삭제된 turn-gate child spec 경로를 현재 계약처럼 가리키는 stale reference가 없다.
- runtime `SKILL.md`, plugin spec, README는 `flow`를 second turn controller로 만들지 않고, `turn-gate`를 turn-level gate로 설명한다.
- question abort recovery가 runtime/spec/scenario에서 같은 의미로 설명된다.
- explicit stop 또는 의도치 않은 terminal-looking closure 뒤 다음 사용자 메시지에서 turn-gate reactivation 계약이 runtime/spec/README/manifest에서 같은 의미로 설명된다.
- flow/turn-gate spec tree에서 runtime instruction과 spec-side fixture가 구분된다.
- flow runtime/spec에 외부 interview skill 호출이나 이름 의존 없이 intent-first discovery 계약이 드러난다.
- flow runtime/spec에 사용자-facing phase label 산출 계약이 드러나고, turn-gate는 이를 재정의하지 않는다.
- flow runtime/spec에 연속 flow의 지속 관점을 위한 목적 계층이 드러난다.
