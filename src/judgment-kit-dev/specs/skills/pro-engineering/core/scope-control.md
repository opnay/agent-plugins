# Scope-Control Contract

## 책임

이 문서는 `pro-engineering`의 탐색 범위 조절을 소유합니다.
좋은 엔지니어링은 모든 단계에서 같은 폭으로 생각하지 않습니다.
자료조사, 문제 공간 파악, 구현 범위 조정처럼 직접 코딩 전 단계에서는 넓게 보고, 실제 구현 단계에서는 선택한 원인과 acceptance signal에 맞춰 좁게 봐야 합니다.

## 넓게 탐색해야 하는 단계

다음 단계에서는 의도적으로 넓은 범위를 봅니다.

- 요구사항, 사용자 흐름, 실패 증상, 기대 동작을 이해할 때
- 어떤 코드 경로, 설정, 데이터, 외부 시스템이 문제에 관여할 수 있는지 찾을 때
- 구현 범위와 non-goal을 정하기 전 대안을 비교할 때
- 변경이 public contract, migration, 권한, 성능, 운영 리스크에 영향을 줄 수 있는지 판단할 때
- 문제를 해결하는 접근이 여러 개이고 제품 의도나 위험 허용 범위가 필요한지 판단할 때

넓게 본다는 것은 무작정 많은 파일을 읽는다는 뜻이 아닙니다.
문제와 연결될 수 있는 후보 영역을 충분히 열어두고, 누락하면 위험한 경계 조건을 먼저 식별한다는 뜻입니다.

## 좁게 집중해야 하는 단계

다음 단계에서는 범위를 좁힙니다.

- 선택한 원인 후보를 검증하는 최소 실험을 만들 때
- 수정할 코드 경로를 정하고 구현에 들어갈 때
- 테스트와 검증을 acceptance signal에 연결할 때
- 리뷰 finding이나 후속 수정에서 bounded blocking issue 하나를 처리할 때

좁게 본다는 것은 주변 맥락을 무시한다는 뜻이 아닙니다.
초기 탐색에서 확인한 경계와 non-goal을 지키면서, 실제 변경은 원인과 결과가 연결되는 최소 표면에 집중한다는 뜻입니다.

## 구현 범위 나누기

- 선택한 구현을 한 번에 완결하고 검증하기 어려우면 동작과 acceptance signal이 이어지는 산출물로 나눕니다.
- 각 산출물은 정상 경로, 관련 실패 경로, 필요한 검증을 포함하고 시스템을 일관된 상태로 남겨야 합니다.
- 파일, 계층, 타입을 따로 만드는 것만으로 구현 단위를 정의하지 않습니다. 각 단위가 제공하는 동작, 계약, 선행 의존성을 설명할 수 있어야 합니다.
- transaction, invariant, ordering이 하나의 단위로 유지되어야 하면 이를 독립 단계로 흩뜨리지 않습니다.

## 전환 기준

넓은 탐색에서 좁은 구현으로 넘어가려면 다음이 필요합니다.

- 문제 설명이 확인 가능한 증상과 기대 동작으로 정리되어 있다.
- 관련 가능성이 있는 영역과 제외해도 되는 영역이 구분되어 있다.
- 선택한 접근이 왜 다른 접근보다 적절한지 설명할 수 있다.
- 구현할 파일, 계약, 테스트 범위가 acceptance signal과 연결되어 있다.
- 범위가 크면 완결 산출물별 acceptance signal과 선행 의존성이 정리되어 있다.

이 기준이 부족하면 바로 코딩하지 말고 discovery를 더 진행하거나 사용자에게 필요한 결정을 물어야 합니다.

## 실패 패턴

- 조사 단계에서 너무 좁게 봐서 실제 원인 경로를 놓친다.
- 구현 단계에서 계속 넓게 벌려 unrelated cleanup이나 speculative refactor를 섞는다.
- 범위 조정 없이 읽은 모든 문제를 같은 commit에 담는다.
- 파일이나 계층별 미완성 조각을 독립 산출물로 취급한다.
- 검증 기준 없이 "좋아 보이는" 구조 개선으로 흐른다.
- 제품 의도 확인이 필요한 문제를 기술적 선호만으로 결정한다.
