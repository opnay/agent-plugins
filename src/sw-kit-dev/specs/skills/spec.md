## 사용자 스펙 의도

- 사용자·제품 요구를 코드에 반영하는 레이어가 필요하다.
- 이 레이어는 제품 기획이 아니라 구현 가능한 행동 계약을 다뤄야 한다.
- `spec`은 무거운 요구사항 문서가 아니라 네 항목의 가벼운 행동 계약으로 동작해야 한다.

# Spec Skill Spec

## 목적

`spec`은 요구를 구현 가능한 가벼운 행동 계약으로 바꾼다. 구현 방법을 정하지 않는다.

## 경계

- 포함: 요청 행동, 중요한 예외와 보존 조건, 관찰 가능한 완료 기준, 열린 결정.
- 제외: 사용자 가치·우선순위·MVP 결정, architecture·data model·technology 선택, source-level 구현.

## 처리 계약

- 확정된 요구와 아직 결정되지 않은 점을 구분한다.
- 사용자가 무엇을 하면 어떤 결과가 일어나는지 적는다.
- 실패, 권한, 기존 행동 보존처럼 결과를 바꾸는 예외만 적는다.
- 완료 기준은 구현 방법이 아닌 관찰 가능한 결과로 쓴다.
- 제품 또는 기술 결정을 요구하는 빈칸은 `open`으로 남긴다.

## 검토 질문

- 구현 전 합의해야 할 행동이 분명한가?
- 중요한 예외와 보존 조건이 빠지지 않았는가?
- 완료를 관찰할 수 있는가?

## 독립성 원칙

제품 handoff를 입력으로 받을 수 있으나, 불완전한 요청만으로도 열린 결정을 드러내며 작업한다. 상태 모델, 연동 계약, 비목표는 실제로 필요할 때만 추가한다.
