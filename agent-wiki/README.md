# Agent Wiki

작업에서 얻은 지식과 경험을 연결된 위키로 축적하고 다음 작업에 재사용합니다.
Rust CLI는 저장 위치·설치를, manager는 작업 관리와 역할 연결을, reader·researcher·writer는 탐색·조사·기억 반영을 담당합니다.


## 스킬 선택

| 스킬 | 시작 조건 | 결과 |
| --- | --- | --- |
| `$agent-wiki:manager` | 작업 준비·진행·정리와 위키 활용을 함께 관리합니다 | 구체 조건·상태·작업/저장 결과, 필요한 전문 역할 연결 |
| `$agent-wiki:reader` | 기존 지식·규칙·프로젝트 이력이 필요합니다 | 관련 문서, 적용 조건, 지식 공백 |
| `$agent-wiki:researcher` | 현재 질문에 근거가 부족하거나 상충·최신성 확인이 필요합니다 | 출처·범위·불확실성을 포함한 조사 결과 |
| `$agent-wiki:writer` | 기억할 사실·결정·자료·작업 상태가 제공됩니다 | 상태·근거를 보존한 프로젝트 소유 기록, 주제별 지식과 저장 검증 |

manager를 기본 진입점으로 사용하며 전문 스킬을 직접 호출해도 됩니다. manager는 조건·진행·완료를 관리하고 필요한 역할만 선택합니다. 기존 문서로 충분하면 reader에서 끝내고 제공된 근거가 충분하면 writer로 바로 반영합니다. manager는 위키 없이 임시 기록으로 진행할 수 있고 위키 읽기·조사·저장에는 해당 전문 runtime을 사용합니다. 고정 순서·전체 스킬 호출·서브에이전트는 필수가 아닙니다.

대표 요청:

- `$agent-wiki:reader 프로젝트 A의 이전 결정과 현재 작업에 적용할 조건을 찾아주세요.`
- `$agent-wiki:researcher 프로젝트 A 기록과 제공한 최신 자료의 차이를 확인해주세요.`
- `$agent-wiki:manager 이번 작업의 구체 조건과 선행·검증 방법을 먼저 정리하고, 필요한 기억을 활용하며 진행 결과를 소유 프로젝트의 같은 작업 기록에 반영해주세요.`
- `$agent-wiki:writer 이 조사 결과와 작업 결정을 소유 프로젝트의 기록과 주제별 지식에 반영해주세요. 본문 링크는 개념·근거·판단에 필요할 때만 사용해주세요. 전달한 체크 상태는 보존하고 근거 공백을 알려주세요.`

## 다중 root 사용

root는 백업·공개·동기화 경계이고, root 안의 폴더는 지식·조사·프로젝트 같은 의미 분류입니다. reader·researcher는 요청·현재 작업·root 이름과 설명에 맞는 root만 읽고 모든 root를 자동 탐색하지 않습니다. 반환 문서는 root 이름과 상대 경로를 함께 표시합니다.

writer는 기록마다 하나의 root를 선택합니다: 사용자 지정, 명확한 현재 작업 root, 이름·설명의 정확한 일치, 비민감하고 모호하지 않은 default 순서입니다. 개인정보나 공개 경계가 섞이거나 대상이 모호하면 먼저 확인합니다. root 사이 Markdown 링크·자동 복사·이동·병합은 만들지 않습니다. root 간 이동은 사용자가 출발 root·대상 root·범위를 명시한 경우에만 수행하며 cross-root 링크를 남기지 않습니다.

## 조건 중심 작업 기록

프로젝트가 작업 기록을 소유합니다. 작업 기록은 선택한 root의 `Projects/<project>/records/`에 두고, 특정 프로젝트가 없는 일반 작업은 `Projects/general/records/`에 둡니다. 프로젝트 지정·기존 프로젝트·작업 맥락을 먼저 확인하며 소유가 불분명하다는 이유만으로 general에 넣지 않습니다. 여러 프로젝트가 관련돼도 주된 책임 프로젝트 하나에 기록하고 복제하지 않습니다. 분류 근거가 없으면 확인합니다.

하나의 의도에는 하나의 기록을 유지합니다. 후속 요청·재개는 기존 조건·상태·정정 이력을 보존하며 같은 문서를 갱신합니다. `Records/` 등 프로젝트 기록 영역 밖의 배치는 지원하지 않습니다. 발견하면 이관 필요와 미저장 내용을 알리며 이관 권한 없이 이전 위치 갱신·이동·복제하지 않습니다. 정확 경로·읽기 전용·기록 금지와 root 공개 경계를 우선합니다.

기록 경로는 `Projects/<project>/records/YYYY-MM/000-<slug>.md`입니다. `YYYY-MM`은 최초 기록 월, `000`은 프로젝트·월별로 000부터 증가하는 세 자리 순번입니다. 기존 최댓값 다음 번호를 사용합니다. 예: `Projects/agent-plugins/records/2026-11/000-record-naming.md`, `Projects/general/records/2026-11/000-local-tool-setup.md`. 후속 요청은 월이 바뀌어도 같은 경로에서 갱신하며 저장 직전 번호 충돌을 확인합니다. 기존 기록의 일괄 이름 변경·이동은 별도 승인 범위입니다.

프로젝트 인덱스 > `records/index.md` > `YYYY-MM/index.md` > 기록으로 하향 안내합니다. 월 폴더는 깊이 4이므로 하위 폴더를 더 만들지 않습니다. 월 인덱스·첨부·숨김 파일을 포함해 직접 파일 25개를 넘으면 저장을 멈추고 필요한 결정을 알립니다. 다른 월이나 번호 폴더로 우회하지 않습니다. 재사용 지식은 기존 소유 주제에 둡니다.

manager는 작업 전에 요청·제약·현재 상태에서 충족 여부를 판단할 수 있는 구체 조건을 정의합니다. 상태·근거·불확실성·선행조건 등은 조건을 빠뜨리지 않기 위한 관점이며 그 자체를 고정 체크 항목으로 만들지 않습니다.

```markdown
- [x] 수정한 기록으로 root 인덱스에서 내려갈 수 있습니다.
  - 결과: root > Projects > 서비스 프로젝트 > 기록 인덱스에서 기록에 도달합니다.
  - 근거: 각 링크와 대상 파일의 존재를 확인했습니다.
- [ ] 기존 소비자가 지원 응답 필드를 계속 사용할 수 있습니다.
  - 검증: 응답 계약과 영향받는 소비자를 대조합니다.
  - 상태: 미확인, 소비자 점검이 남았습니다.
```

- 조건별 하위 일반 목록에 필요한 검증·선행 관계와 결과·근거·적용 조건·한계를 둡니다. 모든 항목에 같은 필드를 채우지는 않습니다.
- 독립적으로 판단할 하위 조건만 체크박스로 나누고 필요한 하위 조건을 모두 충족해야 상위를 완료합니다.
- 확인 근거가 있는 조건만 체크합니다. 진행·실패·보류·미확인·제외는 미완료 표시와 상태·이유로 구분합니다. 완료할 때 하위 결과·근거·한계는 6줄 이내로 요약하고 긴 판단·출처는 별도 절로 연결합니다.
- 준비·수행·완료에서 같은 조건 목록을 갱신하고 조사로 확인한 조건을 보완합니다. 실행 작업 완료와 요청 조건 충족을 각각 대조하며 단계마다 같은 조건을 복제하지 않습니다.
- 작업 중 임시 기록을 원본으로 두고 확정된 중간 결과·의미 있는 실패·전환·중단·완료 시 같은 작업 기록에 반영합니다. 매 도구 호출은 기록하지 않습니다. 재개 시 기존 기록과 대조하고 동시 갱신을 덮어쓰지 않습니다.

프로젝트 소유 작업 기록은 당시 조건·판단·결과를, 소유 주제 문서는 일반화한 지식·사용자 정보를 담당합니다. 새 재사용 지식이 없어도 전달된 작업 기록은 남길 수 있습니다. 자료 생략 판단과 작업 기록 저장은 별개입니다. manager는 확정 중간 결과·중단·완료 시 writer에 기록을 요청하고, writer는 전달된 조건·상태·근거를 보존하며 분류·실제 저장을 검증합니다. 근거가 부족하면 상태를 임의로 바꾸지 않고 불일치를 반환합니다. 작업 완료와 위키 저장 완료는 따로 보고합니다. 두 스킬 모두 제품 구현 권한을 만들지 않습니다.

writer를 직접 호출할 때 manager나 체크리스트는 필수가 아닙니다. 서술형 조사·사용자 정보·과거 결과도 제공 근거 범위에서 기억하며 작업 조건을 새로 도출하거나 완료를 재판정하지 않습니다. 작업 기록 저장이 막히면 미저장 이유를 반환하고 지식 문서에 작업 관찰을 대신 쓰지 않습니다. manager 또는 작업 담당자는 임시 초안과 미반영 상태를 유지합니다.

## 과거 작업과 판단 복원

작업 기록의 본문에서 조건·판단·근거·출처를 읽고 필요한 자료를 참조합니다. 근거 목록·자료 요약은 같은 문서의 절이어도 됩니다. 고정된 링크 사슬이나 세 개의 문서를 요구하지 않으며 본문·출처 식별 정보로 충분하면 추가 위키 링크는 필요하지 않습니다.

- 작업 기록: 문제·목표·제약, 활용 지식, 검토한 대안과 선택·배제 이유, 주요 시도·실패·전환, 결과·검증·한계를 남깁니다.
- 판단별 근거: 무엇을 확인하려 했고 어떤 자료가 실제 판단에 어떻게 쓰였는지, 무엇이 미확인인지 연결합니다.
- 자료 요약: 질문에 필요한 내용, 원문 URL 또는 코드·실험 위치, 확인 날짜·버전·적용 조건·불확실성을 보존합니다.

원인 확인, 대안 선택·배제, 가설 기각, 유의미한 실패·방향 전환, 검증 결과가 나올 때 같은 작업 기록을 갱신합니다. 종료 시 manager 또는 작업 담당자는 누적된 조건·실행 작업과 결과를 대조하며 writer는 전달 상태·근거의 충실한 보존과 실제 저장을 확인합니다. 당시 사실과 후속 정정을 구분하고, 기록되지 않은 판단을 추측하지 않습니다.

`$agent-wiki:reader 과거 로그인 세션 문제를 해결했던 내용을 블로그로 쓰려 합니다. 당시 제약, 참고 지식, 선택 이유, 시행착오와 검증을 관련 출처와 함께 정리해주세요.`

이 요청을 기록 본문과 필요한 근거만으로 설명할 수 있는지가 완료 기준입니다. reader는 조건·변경 이유·충족 여부·미충족 결과와 한계를 복원하며 체크 표시만으로 완료를 확정하지 않습니다. 기존 서술형 기록도 읽고 없는 조건·판단은 공백으로 알립니다.

위키 기록의 완료 기준은 당시 관찰·판단·조건·한계를 이해할 수 있는 것입니다. 모든 실험의 재실행이나 원시 자료 보존을 요구하지 않습니다. writer는 필요한 결과를 본문에 요약하고 임시 폴더를 지속적인 근거로 사용하지 않습니다. 단기 복구·인계에 필요한 임시 위치는 용도와 임시성을 구분하며, 근거를 만들기 위한 자동 아카이빙은 하지 않습니다.

## URL 조사 위임과 재사용

기존 위키를 찾을 때 정확한 문서 경로는 직접 읽고, 그 외에는 root·하위 인덱스로 영역을 고른 뒤 관련 링크와 영역 내 검색을 사용합니다. 인덱스가 없거나 불완전하거나 선택 영역에서 찾지 못할 때만 필요한 범위로 검색을 넓힙니다. 충분한 제공 자료는 재조회하지 않습니다. 이 순서는 지식 조회 기준입니다. writer의 승인된 이동·병합에서는 선택 root 안의 들어오는 참조를 별도로 탐색하며, 명시적 전체 정리·감사는 writer 또는 해당 승인 워크플로의 범위에서 검사합니다. reader·researcher의 일반 조회를 자발적인 전역 감사로 넓히지 않습니다.

먼저 기존 위키의 관련 범위·출처·확인 날짜를 확인합니다. 충분하면 재사용하고 버전 변화·상충·근거 공백이 현재 판단에 영향을 줄 때 해당 부분만 재조회합니다.

독립적으로 분리 가능한 자료 확인은 위임이 허용된 경우 서브에이전트에 맡길 수 있습니다. 다음처럼 조사 목적과 기록 권한을 함께 전달합니다.

> 질문: 토큰 회전 환경에서 동시 갱신 요청이 실패하는 조건을 확인해주세요. 자료: 지정 URL 목록과 기존 위키 문서 경로. 필요한 정보: 적용 버전·동시 요청 조건·실패 동작. `$agent-wiki:researcher`로 근거를 확인하고 `$agent-wiki:writer`로 승인된 위키 루트와 문서 범위 안에 정리해주세요. 저장 문서 경로·핵심 발견·미해결 항목·저장 상태만 반환해주세요.

실제 위임 시 URL·경로·허용 쓰기 범위와 접근 가능한 스킬 경로 또는 식별자를 구체적으로 전달합니다. researcher는 읽기 전용이며, 저장은 writer 역할로 전환한 뒤 수행합니다. 같은 문서는 담당을 하나로 정하거나 쓰기를 직렬화합니다. 저장 실패와 조사 성공은 구분합니다.

메인은 반환된 문서의 필요한 부분과 판단 관련 출처를 확인하고, 실제 채택·배제와 이유를 작업 기록에 남깁니다. 자료 담당자는 메인의 판단을 추측하지 않습니다. 위임은 필수가 아니며, 반복 조회와 메인 문맥을 줄일 수 있지만 서브에이전트까지 포함한 총 토큰 절감을 보장하지 않습니다.

## 기록·연결·정리

위키 기록이 허용된 작업에서는 새 근거·사용자 정보·확정된 중간 결과를 자주 반영합니다. 이미 승인된 기록을 매번 다시 묻지는 않지만, 위치 설정만으로 쓰기 권한이 생기는 것은 아닙니다. 읽기 전용·기록 금지 요청과 상위 권한 제한을 따릅니다.

지식은 실제 내용의 분야·하위 주제로 분류하며 계층 수·분야 목록·문서 템플릿을 고정하지 않습니다. writer는 소유 주제·적용 범위·문서 역할을 판단하고 같은 질문은 갱신, 별개 질문은 독립 문서로 기록합니다. 같은 주제의 현재 내용을 독립 본문 2개 이상으로 나눌 수 있으면 기존 파일 수와 무관하게 즉시 주제 폴더를 구성하고 분리합니다. index.md는 이 개수에서 제외합니다. 단일 질문은 구체명 문서로 두고 서로 다른 주제는 각 소유 위치로 나눕니다. 미래 확장만 예상한 빈 구조·기계적인 분할은 만들지 않으며 기존 단일 자식 폴더를 자동 해체하지 않습니다.

폴더는 주제명, 일반 파일은 구체 내용을 사용합니다. 예를 들어 좌표·레이아웃 해석 문서 하나는 `design/tools/figma-coordinates-and-layout.md`, Figma의 독립 본문 둘 이상은 `design/tools/figma/` 아래에 둡니다. 경로는 예시이며 split view 같은 일반 UI 패턴을 Figma 하위 문서 수로 세지 않습니다. 신규 지식 발굴 요청은 기존 본문 보충과 독립 주제 검토를 구분하고 새 문서·갱신·중복 생략·미확인 범위를 보고합니다.

재사용 개념·방법·사례와 프로젝트 고유 설계·정책의 소유를 구분합니다. 분리·이름 변경·이동은 승인 범위에서 내용·출처·조건·정정·인덱스·영향 링크를 보존하며 의미상 배치와 실제 저장을 확인합니다. 빈 위키는 최소 index.md로 시작하고 CLI의 set은 문서를 만들지 않습니다.

폴더 트리는 상위 위치를 제공하고 `index.md`는 영역의 목적·범위와 하위 주제·문서의 역할을 설명해 다음 읽을 대상을 top-down으로 안내합니다. 일반 문서와 작업 기록의 본문 링크는 개념 이해·주장이나 관찰의 근거·선택과 배제 및 적용 조건의 판단에 필요할 때 사용합니다. 관계는 본문 문맥에서 알 수 있으면 되며 별도 설명 필드는 강제하지 않습니다. 같은 작업에서 작성·수정·조회했거나 같은 프로젝트에 속한다는 사실만으로 연결하지 않습니다. 작업 기록은 해결한 질문·발견·판단·결과·검증 한계를 설명하며 수정 문서 목록을 기본 생성하지 않습니다. 링크는 해당 설명에 필요한 대상에 직접 둡니다. 인덱스의 탐색 목록과 실제 출처·근거 목록은 유지합니다. 전체 변경 목록은 명시 요청 또는 파일별 검증에 필수인 경우에만 제공하고 기존 diff·manifest를 우선 사용합니다. 별도 감사 파일을 자동 생성하지 않습니다. 필요한 방향은 각각 판단하며 기계적인 왕복이나 위치 복귀용 상위·루트 링크를 넣지 않습니다. 작업 기록에도 필요한 판단 근거가 있다면 해당 문서나 절을 참조할 수 있습니다. React 개요는 `Knowledge/React/index.md`, React 19 변경사항은 `Knowledge/React/19.md`처럼 정확한 내용을 가진 대상을 가리킵니다. 경로는 예시입니다.

각 root의 인덱스에서 하위 영역과 문서로 도달할 수 있어야 합니다. 검증은 하향 도달성과 링크 대상 유효성을 확인하며 문서에서 root로의 복귀나 양방향 링크는 요구하지 않습니다. 기존 위치 복귀 링크의 삭제는 승인된 탐색 정리 범위에 한정하며 일반 내용 수정에 덧붙이지 않습니다. 상위 인덱스라도 의미 있는 개요·근거 참조는 보존합니다. 부분 탐색에서 경로를 찾지 못한 것은 확인 영역의 공백으로 보고하며 전체 고립으로 단정하지 않습니다. 작성할 때 주변을 정리하고 작업 종료 시 변경 범위를 점검합니다. 일반 이동·병합은 같은 root 안에서 기존 내용과 참조를 보존합니다. root 간 이동은 사용자가 출발 root·대상 root·범위를 명시한 경우에만 수행하며 cross-root Markdown 의존성을 남기지 않습니다.

설정·접근이 불가능하면 다른 폴더에 임의 기록하지 않고 본 작업과 위키 미반영 상태를 구분합니다. reader·researcher는 위키를 수정하지 않습니다.

## 웹 조사 결과 반영

웹 조사 후에는 기록 필요성을 항상 판단하며, 실제 기록은 다음 기준을 따릅니다.

- 새 사실·방법·제약, 비교·선택·배제의 근거, 기존 위키의 오류·누락·오래된 정보 정정은 기록합니다.
- 페이지 찾기·실패한 검색·내용 없는 탐색이나 추가 근거·조건이 없는 중복은 생략합니다.
- 날씨·가격·일정 같은 일시적 정보는 작업 결정의 근거일 때만 날짜와 함께 남깁니다.
- 기존 내용 재확인은 도움이 될 때 확인 시점·근거만 갱신합니다.
- 검색어나 방문 페이지별로 파일을 만들지 않고, 해결한 질문과 결과별로 출처·범위·확인 시점을 묶습니다.

writer는 다른 도구·스킬의 조사 결과도 받아 판단합니다. researcher 재실행은 필요하지 않으며 기존 기록 권한·읽기 전용·기록 금지 조건은 유지됩니다.

## 폴더 제한

- 각 root의 폴더당 직접 파일은 `index.md`·첨부·숨김 파일을 포함해 최대 25개입니다. 하위 폴더와 ZIP 내부 항목은 합산하지 않습니다.
- 각 root는 깊이 0이며 최대 깊이는 4입니다. `wiki/A/B/C/D/document.md`까지 허용합니다.
- 단순 폴더명과 서브 카테고리는 자유롭게 정합니다. 밑줄 복합명은 `<상위>_<하위>` 두 부분까지만 사용합니다. `react_hooks`는 허용하고 `react_hooks_effect`는 사용하지 않습니다. 더 세분화하려면 `react_hooks/effect/`처럼 실제 폴더를 나눕니다. 파일명에는 적용하지 않습니다.
- writer는 생성·이동 전에 상한을 확인합니다. 초과하면 의미 있는 주제로 분류하되 무관한 내용을 합치거나 삭제하지 않습니다. reader·researcher는 발견한 위반만 알립니다.

## 설치

macOS·Linux용 Rust 단일 실행 파일입니다. 설치와 실행에는 Python이나 Rust 런타임이 필요하지 않습니다.
이 README가 있는 플러그인 폴더에서 실행합니다.

```sh
./scripts/agent-wiki install
```

`~/.local/bin/agent-wiki`에 현재 실행 파일 하나를 복사합니다. 원본 플러그인 폴더나 별도 라이브러리 파일에 의존하지 않습니다. 바이너리는 빌드한 OS·아키텍처에 맞춰 사용합니다.
동일한 파일은 그대로 유지하며, 다른 기존 파일을 교체하려면 내용을 확인한 뒤 `install --force`를 사용합니다. 심볼릭 링크와 디렉터리는 교체하지 않습니다.

소스 체크아웃에는 바이너리를 저장하지 않습니다. 바이너리가 없다면 Rust/Cargo를 준비하고 먼저 빌드합니다.

```sh
sh scripts/build.sh
./scripts/agent-wiki install
```

빌드 시 Cargo.lock에 고정된 의존성을 가져옵니다. 완성된 `scripts/agent-wiki` 파일만 복사해 다른 동일 플랫폼 환경에서도 설치할 수 있습니다.

`~/.local/bin`이 PATH에 없다면 셸 설정에 다음 내용을 추가합니다.

```sh
export PATH="$HOME/.local/bin:$PATH"
```

## 저장 위치 설정·조회

root는 백업·공개·동기화의 물리 경계이고, root 안의 폴더는 지식·조사·프로젝트 같은 의미 분류입니다. root 이름은 사용자가 정합니다. 같은 basedir 아래의 여러 root도 서로 다른 경계이지만, basedir 전체를 백업하면 모두 포함될 수 있습니다.

서로 같은 경로나 상하로 중첩된 root는 등록할 수 없고 형제 root는 허용합니다. root 사이 상대 Markdown 링크는 만들지 않습니다.

```sh
agent-wiki set knowledge ~/Documents/Wiki
agent-wiki set personality ~/.agents/personality
agent-wiki default knowledge
agent-wiki list
agent-wiki path knowledge
agent-wiki path
agent-wiki --help
```

`set <name> <directory>`로 root 이름과 경로를 명시합니다. 설치는 저장 위치를 정하지 않습니다. `set` 또는 `default`는 `~/.agents/config.wiki.toml`을 원자적으로 갱신합니다.

`list`는 각 root의 이름, canonical 경로, default 여부, 선택용 description을 탭 구분 필드로 출력합니다. description이 없으면 `-`를 출력합니다.

```toml
default = "knowledge"

[roots.knowledge]
path = "/Users/example/Documents/Wiki"
description = "Shared knowledge"

[roots.personality]
path = "/Users/example/.agents/personality"
```

- 설정은 `default`와 named `roots`로 구성합니다. `root = "/absolute/path"` 형식과 `set <directory>`는 거부하며 기존 설정을 보존합니다. 자동 변환은 하지 않습니다.
- `set`은 폴더가 없거나 파일이면 실패하며, 중복·중첩 root도 거부하고 기존 설정을 보존합니다.
- `path [name]`은 설정되지 않았거나 root 경계가 유효하지 않다면 실패하고 canonical 경로를 출력합니다. `list`도 전체 root의 중복·중첩·존재 여부를 검증한 뒤 이름·canonical 경로·default 여부·description을 보여줍니다.
- 설정 파일이 심볼릭 링크이면 링크를 유지하고 실제 대상 파일을 조회·갱신합니다. 갱신은 원자적 교체를 사용하며, 끊어진 링크는 수정하지 않고 실패합니다.
- 설정 파싱이나 갱신 결과의 root 검증에 실패하면 기존 파일을 보존합니다. `set <name> <directory>`로 같은 root의 경로를 정정할 수 있습니다. 주석과 서식은 갱신 시 정규화합니다.
- 도움말과 조회는 파일을 생성하지 않습니다. 셸 설정과 위키 내용도 변경하지 않습니다.
