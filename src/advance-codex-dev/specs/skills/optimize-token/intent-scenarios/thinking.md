# Thinking Intent Scenarios

이 문서는 `optimize-token`의 작업 전 thinking/progress 표면에 `light`, `standard`, `extreme` 호출 강도를 적용하는 의도를 예시로 고정합니다.
목적은 답변이나 작업 전에 사용자에게 보이는 판단 문장과 진행 보고를 선택된 강도에 맞게 간결하고 실행 가능하게 만드는 것입니다.

## 판정 기준

- 사용자 의도, 다음 행동, 검증 필요성, 승인 경계처럼 작업을 바꾸는 정보는 유지합니다.
- "같습니다", "수 있습니다", "좋겠습니다" 같은 완충 표현은 근거가 충분하면 더 직접적인 판단으로 줄입니다.
- 실제 불확실성은 지우지 않습니다.
- thinking 최적화는 간결한 작업 전 판단과 사용자에게 보이는 진행 보고에 적용합니다. 내부 추론 공개를 요구하지 않습니다.
- `light`, `standard`, `extreme`은 skill 호출 전체의 압축 강도이며, thinking/progress 표면에도 적용됩니다.
- 호출 모드가 명시되면 그 모드를 따릅니다. 호출 모드가 명시되지 않았을 때만 요청과 위험도에 맞는 가장 약한 충분한 압축 강도를 추정합니다.
- 최종 답변 작성 규칙은 runtime `references/response.md`가 소유합니다. 이 문서는 작업 전 판단 문장 예시만 소유합니다.

## 예시

### 설명 요청 후 구현 의향 확인

- Before: `사용자가 설명을 원하는 것 같습니다. 자세한 답변을 제공한 후 구현해 볼 의향이 있는지 물어볼 수 있습니다.`
- light: `사용자가 설명을 원하므로, 답변 후 구현 의향을 확인합니다.`
- standard: `설명 후 구현 의향을 확인합니다.`
- extreme: `다음: 설명 후 구현 여부 확인.`
- 모드 차이: `light`는 의도와 다음 행동을 자연문으로 유지하고, `standard`는 실행 행동만 더 조밀하게 남기며, `extreme`은 다음 행동 라벨로 고정합니다.

### 관련 파일 확인

- Before: `이 작업은 파일을 수정해야 할 가능성이 있어 보이므로 먼저 관련 파일을 확인하는 것이 좋겠습니다.`
- light: `파일 수정 가능성이 있으므로 관련 파일을 먼저 확인합니다.`
- standard: `관련 파일을 먼저 확인합니다.`
- extreme: `다음: 파일 확인.`
- 모드 차이: `light`는 작업 이유와 다음 행동을 함께 남기고, `standard`와 `extreme`은 이유를 줄이고 다음 행동 중심으로 압축합니다.

### 검증 필요성

- Before: `변경이 끝나면 문제가 해결됐는지 확인하기 위해 테스트를 실행하는 방향이 적절해 보입니다.`
- light: `변경 후 테스트로 해결 여부를 확인합니다.`
- standard: `테스트로 해결 여부를 확인합니다.`
- extreme: `검증: 테스트.`
- 모드 차이: 세 모드 모두 검증 필요성을 보존하며, 강도가 높아질수록 문장형에서 라벨형으로 이동합니다.

### 불확실성 유지

- Before: `이 실패가 sandbox 때문인지 코드 문제인지는 아직 확실하지 않으므로, 로그와 재현 조건을 먼저 확인해야 할 것 같습니다.`
- light: `sandbox 문제인지 코드 문제인지 불확실하므로, 로그와 재현 조건을 먼저 확인합니다.`
- standard: `원인이 불확실해 로그와 재현 조건을 확인합니다.`
- extreme: `불확실: sandbox/code. 다음: 로그, 재현 조건 확인.`
- 모드 차이: 세 모드 모두 실제 불확실성과 다음 행동을 남깁니다.

### 승인 경계 유지

- Before: `이 명령은 외부 네트워크 접근이 필요할 수 있으므로, 실패하면 승인을 요청해서 다시 실행해야 할 수 있습니다.`
- light: `외부 네트워크 접근이 필요할 수 있으므로, 실패하면 승인 후 재실행합니다.`
- standard: `네트워크 문제로 실패하면 승인 후 재실행합니다.`
- extreme: `승인 경계: 네트워크 실패 시 재실행 승인 필요.`
- 모드 차이: 세 모드 모두 승인 조건과 재실행 조건을 남깁니다.

### 과압축 실패 예시

- Before: `검증은 아직 실행하지 않았고, 변경 범위가 넓어 회귀 위험이 남아 있습니다.`
- light: `검증은 아직 실행하지 않았고, 넓은 변경 범위로 회귀 위험이 남아 있습니다.`
- standard: `미검증이며 회귀 위험이 남아 있습니다.`
- extreme: `상태: 미검증. 위험: 회귀 가능.`
- 모드 차이: 세 모드 모두 미검증과 위험을 남기며, `extreme`도 실패 상태를 숨기지 않습니다.

### 사용자 정정 반영

- Before: `제가 사용자의 의도를 잘못 이해한 것 같습니다. 이전 답변의 방향을 수정해서 다시 설명해야 할 것 같습니다.`
- light: `이전 해석을 수정하고, 사용자의 의도에 맞춰 다시 설명합니다.`
- standard: `해석을 수정해 다시 설명합니다.`
- extreme: `다음: 해석 수정 후 재설명.`
- 모드 차이: 세 모드 모두 정정 사실과 다음 행동을 남깁니다.

### 작업 범위 제한

- Before: `이 변경과 직접 관련 없는 파일은 건드리지 않는 편이 좋겠습니다. 현재 요청 범위에 포함된 파일만 확인하고 수정해야 할 것 같습니다.`
- light: `관련 없는 파일은 제외하고, 요청 범위의 파일만 확인하고 수정합니다.`
- standard: `요청 범위 파일만 확인하고 수정합니다.`
- extreme: `범위: 요청 파일만.`
- 모드 차이: 세 모드 모두 범위 제한을 안전 경계로 보존합니다.

### 질문 라우팅

- Before: `이 경우에는 사용자의 선택에 따라 구현 방향이 달라질 수 있으므로, 먼저 어떤 방향을 원하는지 물어보는 것이 좋을 수 있습니다.`
- light: `구현 방향이 사용자 선택에 따라 달라지므로, 먼저 방향을 확인합니다.`
- standard: `사용자 선택이 필요해 방향을 확인합니다.`
- extreme: `질문: 구현 방향 확인.`
- 모드 차이: 세 모드 모두 질문 필요성과 다음 행동을 남깁니다.
