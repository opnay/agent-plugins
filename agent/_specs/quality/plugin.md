# Quality 플러그인 스펙

## 플러그인 목적

`quality`는 산출물의 목적·특성·영향에 맞는 품질 기준과 검증 절차를 도출하고, 실제 근거로 판단하는 에이전트 행동 패턴을 제공합니다. 적용 분야와 품질 축은 열린 범위입니다. 산출물은 코드·화면·문서·계획·조사·데이터 및 복합 결과물을 포함하며 이 목록으로 제한하지 않습니다.

## 이름과 경계

- plugin 이름: `quality`, 표시 이름: `Quality`.
- 그룹: `agent`. 역할군별 실행 환경에 함께 설치해 사용하는 공통 행동 패턴입니다.
- 핵심 skill: `verify`. 호출 식별자: `$quality:verify`.
- 포함: 산출물 이해, 검증 축·기준 도출, 근거의 적합성 판단, 검증 방법 선택·실행, 결함·미검증·남은 위험 보고, 필요한 재검증 범위 결정.
- 제외: 전문 지식·도구·원본 근거가 없는 상태의 품질 보증, 기능 제작·수정·배포 권한 부여, 제품 목표·사업 정책 변경, 범용 작업 배치·모델 프로필·subagent 생성 정책, 독립 인증이나 출시 승인 대체.
- 전문 분야의 기준은 사용자 자료·프로젝트 규칙·확인한 전문 지식·사용 가능한 역할 skill에서 확보합니다. 특정 역할 skill의 선행 호출이나 설치를 요구하지 않습니다.

## 처리하려는 작업 형태

- 산출물이 목적·요구·제약을 충족하는지 실제로 검증합니다.
- 동작뿐 아니라 구조·표현·논리·근거·수치·상호작용·변경 영향에서 필요한 품질 축을 찾습니다. 축은 고정 체크리스트가 아닙니다.
- 하나의 산출물에 여러 분야의 특성이 섞이면 관련 기준과 검증을 결합합니다.
- 검증 계획만 요청하면 절차와 필요한 근거를 설계하고, 검증 실행과 구분합니다.
- 작성 에이전트와 별도 검토 에이전트가 같은 계약을 사용할 수 있습니다. 독립성은 이름이나 agent 생성만으로 성립하지 않으며 입력·맥락·근거로 판단합니다.

## 대표 표면

- 작성 계약: `agent/_specs/quality/plugin.md`, [verify spec](skills/verify/spec.md).
- 사용자 의도: [verify intent](skills/verify/intent.md).
- 구현 대상: `agent/quality/README.md`, 두 호스트 `plugin.json`, `skills/verify/SKILL.md`.
- 사용 안내 문구: “산출물의 목적과 특성에 맞는 검증 기준·절차를 도출하고, 허용된 검증을 수행해 근거·판정·미검증을 반환합니다.”
- manifest 설명·prompt는 실제 제공 skill과 실행 조건만 안내합니다. 설치가 전문성·실행 권한·검증 성공을 보증한다고 설명하지 않습니다.

## 내장 skill 체계

`verify` 하나가 분석부터 판정까지의 응집된 작업을 소유합니다. 계획·실행·보고는 이 skill의 단계이며 각각 별도 skill로 나누지 않습니다. 상세 입력·방법 선택·근거·상태·종료 계약은 [skill spec](skills/verify/spec.md)이 소유합니다.

## 사용과 조합

- 역할군 에이전트: 전문 기준과 프로젝트 맥락을 제공하고 `verify`가 현재 산출물에 맞는 검증 절차를 설계·수행합니다.
- 오케스트레이터: 작업 배치·의존성·통합을 소유하고 검증 작업에 이 계약을 연결합니다. 직접 검증도 가능하며 오케스트레이터는 필수 의존성이 아닙니다.
- subagent: 부모가 기존 권한과 실행 수단으로 배정할 수 있습니다. 패킷에는 대상 버전·원본 요구·목적·제약·허용 범위·근거 출력 형식을 담습니다. 검토자는 작성자의 성공 주장에 의존하지 않고 실제 결과를 확인합니다. 위임받은 검토자는 별도 위임 권한을 얻지 않습니다.
- 작업 관리자: 전체 의도·진행·요구 변경을 소유합니다. `verify`는 배정된 산출물·범위의 검증을 소유하며 전체 목표를 변경하지 않습니다. 발견한 조건 공백은 근거와 영향으로 반환합니다.
- 전문 skill: 분야의 판단 기준·기법을 제공하고 quality는 적용할 검증 축·방법·근거를 연결합니다. 전문 기준을 포괄적 체크리스트로 복제하지 않습니다.
- 기존 `pro-quality-manager`: 현재 plugin과 호출을 유지합니다. 새 설계는 단순 이름 변경이나 자동 대체가 아닙니다. 중복 계약의 추출·정리와 사용 표면 migration은 별도 구현 범위에서 결정합니다.
  - 현재 산출물을 실제로 조사·실행·대조해 검증 근거와 판정을 만들 때는 `verify`를 선택합니다. 프로젝트·release의 품질 목표·검증 공백·리스크 우선순위·출시 근거를 종합 관리할 때는 기존 `pro-quality-manager`의 범위입니다.
  - 두 작업이 함께 필요하면 품질 관리에서 식별한 검증 질문·기준을 verify에 전달하고 실제 결과를 품질 판단의 근거로 사용합니다. 서로의 선행 호출을 요구하지 않으며 품질 관리 보고서가 검증 실행을 대신하지 않습니다.

## SDD와 확장 원칙

- runtime은 설치된 본문·리소스만으로 실행 가능해야 하며 `_specs`·orcat·특정 외부 서비스에 의존하지 않습니다.
- 신규 skill은 별도 사용자 목적·산출물·선택 기준이 있을 때만 검토합니다. 분야별 동일 흐름의 복사나 단계별 분리를 하지 않습니다.
- 구현 시 두 manifest의 metadata와 실제 제공 skill, README·marketplace·spec을 맞춥니다. 그룹은 plugin 이름과 호출에 포함하지 않습니다.
- [검증 계획](validation-plan.md)으로 계약 충족과 행동 효과를 분리해 확인합니다. 설계 검토는 실제 설치·선택·모델 행동 검증을 대신하지 않습니다.
