## 사용자 스펙 의도

- 사용자·제품 요구를 코드에 반영하는 레이어가 필요하다.
- 이 레이어는 제품 기획이 아니라 구현 가능한 행동 계약을 다뤄야 한다.

---

# Spec Skill Spec

## 목적

`spec`은 요구를 소프트웨어 행동 계약으로 바꾼다. 구현 방법을 정하지 않고, 무엇이 어떤 상태에서 어떻게 동작해야 하는지 명확히 한다.

## 경계

- 포함: actor, trigger, state, rule, exception, integration point, non-goal, 기술 중립 acceptance criteria.
- 제외: 사용자 가치·우선순위·MVP 결정, architecture·data model·technology 선택, source-level 구현.

## 처리 계약

- 입력에서 확정 사항, 가정, 열린 질문을 분리한다.
- 정상 흐름뿐 아니라 상태 전이, 실패·권한·빈 데이터·복구 조건을 명시한다.
- 외부 시스템과 보존해야 할 기존 행동을 경계로 적는다.
- acceptance criteria는 관찰 가능한 결과로 쓰고 구현 방법을 강제하지 않는다.
- 결정이 필요한 빈칸은 숨기지 않고 질문 또는 가정으로 남긴다.

## 검토 질문

- 누가 어떤 조건에서 무엇을 할 수 있는가?
- 상태와 예외에서 기대 결과는 무엇인가?
- 연동 경계와 비목표가 분명한가?
- 구현 선택을 섞지 않은 채 검증할 수 있는가?

## 독립성 원칙

제품 handoff를 입력으로 받을 수 있으나, 불완전한 요청만으로도 필요한 질문과 임시 가정을 드러내며 작업한다.
